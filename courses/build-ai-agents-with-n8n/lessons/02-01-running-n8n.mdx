Before assembling complex AI agent loops, you must make a foundational architectural decision: should you run n8n in **n8n Cloud** or **self-host** it on your own infrastructure?

This decision impacts your operational cost, data privacy, scaling limits, and maintenance responsibilities.

## Clarifying "Cloud" vs "Self-Hosted"

In the n8n ecosystem, these terms have precise technical meanings:

- **n8n Cloud**: The official managed SaaS platform hosted by the n8n team. You register, log in, and immediately begin constructing workflows. Servers, SSL certificates, database tuning, automatic backups, and high-availability queues are managed entirely for you.
- **Self-Hosting**: You operate the n8n application on infrastructure you control. This includes a bare-metal server, a home lab Raspberry Pi, an AWS EC2 instance, or managed VPS providers like DigitalOcean, Render, or Hostinger.

<Callout type="info" title="VPS Hosting is Still Self-Hosting">
When you deploy n8n on a cloud VPS provider like Hostinger, DigitalOcean, or AWS, the hardware resides in a remote data center, but you remain the systems administrator. You configure Docker, manage database migrations, issue SSL certificates, and apply version updates. Therefore, it is classified as **self-hosting**.
</Callout>

## Tradeoff Matrix: n8n Cloud vs Self-Hosting

| Feature | n8n Cloud | Self-Hosted (Docker on VPS) |
| :--- | :--- | :--- |
| **Setup Time** | Under 2 minutes | 15 to 45 minutes |
| **Maintenance Burden** | Zero maintenance; fully managed | You manage OS patches, Docker updates, backups |
| **Pricing Model** | Tiered subscription based on workflow executions | Flat VPS cost ($5 to $20/month) + zero software fees |
| **Execution Limits** | 1,000 to 10,000+ runs per month by plan tier | Unlimited workflow executions |
| **Data Privacy & Compliance** | Data processed in n8n Cloud EU data centers | 100% on-premise; complies with HIPAA, GDPR, SOC 2 |
| **Network Access** | Public endpoints with managed domain | Direct access to internal private VPC subnets & databases |
| **Recommended For** | Beginners, agencies, fast prototyping | Engineers, enterprises, high-volume agent loops |

## Production Docker Compose Configuration

For self-hosting, the industry standard is running n8n alongside a dedicated **PostgreSQL** database container via Docker Compose. SQLite is default for quick local tests, but PostgreSQL is required for high-throughput production environments and concurrent agent execution.

Here is a hardened `docker-compose.yml` configuration:

```yaml
version: '3.8'

services:
  postgres:
    image: postgres:16-alpine
    restart: always
    environment:
      - POSTGRES_USER=n8n
      - POSTGRES_PASSWORD=replace_with_strong_database_password
      - POSTGRES_DB=n8n
    volumes:
      - postgres_storage:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h localhost -U n8n -d n8n"]
      interval: 5s
      timeout: 5s
      retries: 10

  n8n:
    image: docker.n8n.io/n8nio/n8n:latest
    restart: always
    ports:
      - "5678:5678"
    environment:
      # Database Backend
      - DB_TYPE=postgresdb
      - DB_POSTGRESDB_HOST=postgres
      - DB_POSTGRESDB_PORT=5432
      - DB_POSTGRESDB_DATABASE=n8n
      - DB_POSTGRESDB_USER=n8n
      - DB_POSTGRESDB_PASSWORD=replace_with_strong_database_password
      # Security & Encryption Key
      - N8N_ENCRYPTION_KEY=generate_a_random_32_character_hex_key
      - N8N_HOST=n8n.yourdomain.com
      - N8N_PORT=5678
      - N8N_PROTOCOL=https
      # Webhook Configuration
      - WEBHOOK_URL=https://n8n.yourdomain.com/
      # Timezone
      - GENERIC_TIMEZONE=America/New_York
      # Execution Data Pruning (keeps database lightweight)
      - EXECUTIONS_DATA_PRUNE=true
      - EXECUTIONS_DATA_MAX_AGE=168 # 7 days in hours
    volumes:
      - n8n_storage:/home/node/.n8n
    depends_on:
      postgres:
        condition: service_healthy

volumes:
  postgres_storage:
  n8n_storage:
```

### Critical Environment Variables Explained
- `N8N_ENCRYPTION_KEY`: A persistent cryptographic key used to encrypt your saved credentials (API tokens, OAuth2 secrets) in the database. Never lose or change this key after initialization, or all saved credentials will become unreadable.
- `WEBHOOK_URL`: The fully qualified public URL where third-party webhooks (Stripe, GitHub, Telegram) deliver incoming payloads.
- `EXECUTIONS_DATA_PRUNE`: In production, storing every execution log forever will exhaust server disk space. Setting `EXECUTIONS_DATA_PRUNE=true` automatically discards successful run logs older than a designated age (e.g. 7 days) while retaining error logs for debugging.

<Exercise title="Identify Deployment Failures">
An engineer deploys n8n using Docker on a remote VPS. When they trigger a Telegram bot webhook, Telegram reports `HTTP 404` or `Connection Refused`, even though the workflow is active in the canvas. What environment variable was likely misconfigured?

<SolutionToggle>
The issue is almost certainly `WEBHOOK_URL`. 

If `WEBHOOK_URL` is omitted or left as `http://localhost:5678/`, n8n will register `localhost` with external services during webhook activation. Telegram's servers cannot reach `localhost`. Setting `WEBHOOK_URL=https://n8n.yourdomain.com/` ensures n8n registers the public, routable HTTPS domain.
</SolutionToggle>
</Exercise>
