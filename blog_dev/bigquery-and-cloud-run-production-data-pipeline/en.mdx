## 1. Architecture Overview: Serverless Data Ingestion

Our serverless data ingestion pipeline is designed for high-throughput, low-latency event processing, delivering data reliably into BigQuery for analytics. The core principle is to leverage managed services to minimize operational overhead and maximize scalability.

Here's the end-to-end flow:

1.  **Event Source:** Any application or service generating data (e.g., webhooks, IoT devices, internal microservices).
2.  **Publisher (Optional but Recommended):** Events are published to a Pub/Sub topic. This provides decoupling, buffering, and built-in retry mechanisms, enhancing reliability and handling bursts. For direct HTTP ingestion, this layer is skipped.
3.  **Cloud Run Receiver:** A stateless HTTP service (implemented with FastAPI) deployed on Cloud Run. It receives events (either directly via HTTP or pulled from Pub/Sub via a push subscription), validates them, and then streams them to BigQuery.
4.  **BigQuery Storage Write API:** The Cloud Run service uses the BigQuery Storage Write API for efficient, reliable, and exactly-once data ingestion into BigQuery.
5.  **BigQuery Table:** Data lands in a BigQuery table, typically partitioned by event time and clustered by relevant dimensions, optimizing query performance and reducing costs.
6.  **Downstream Consumers:** Once in BigQuery, data is available for analytics, dashboards (Looker Studio, Power BI), machine learning models, or further transformations (dbt, Dataflow).

```
+----------------+       +-----------+       +---------------+       +---------------------+       +----------------+       +-------------------+
|                |       |           |       |               |       |                     |       |                |       |                   |
|  Event Source  +------>|  Pub/Sub  +------>|  Cloud Run    +------>|  BigQuery Storage   +------>|  BigQuery      +------>|  Downstream       |
| (Application,  |       |   Topic   |       |  (FastAPI     |       |    Write API        |       |  Table         |       |  Consumers        |
|  IoT, Webhook) |       |           |       |   Receiver)   |       |                     |       | (Partitioned,  |       | (Analytics, ML,   |
|                |       |           |       |               |       |                     |       |  Clustered)    |       |  Dashboards)      |
+----------------+       +-----------+       +---------------+       +---------------------+       +----------------+       +-------------------+
        ^                                            |                                                      ^
        |                                            |                                                      |
        |                                            +------------------------------------------------------+
        |                                                    (Error Handling, DLQ, Monitoring)
        |
        +-----------------------------------------------------------------------------------------------------
                                                              (Direct HTTP Ingestion - bypasses Pub/Sub)
```

This architecture is entirely serverless, meaning no servers to provision, patch, or manage. Scaling is automatic, driven by demand.

## 2. The BigQuery Storage Write API: Streaming Done Right

For high-volume, real-time data ingestion into BigQuery, the Storage Write API is the definitive choice. It supersedes older methods like the legacy JSON streaming inserts (which are still available but generally discouraged for new, high-performance pipelines) and batch loading via Cloud Storage.

### Why Storage Write API Beats Legacy Streaming

The legacy JSON streaming insert API (`tabledata.insertAll`) has several limitations:
*   **Cost:** It's more expensive per row.
*   **Throughput:** Lower throughput limits.
*   **Reliability:** Best-effort semantics, requiring client-side deduplication for exactly-once processing.
*   **Schema Evolution:** Less flexible, requiring careful handling of schema changes.

The BigQuery Storage Write API addresses these shortcomings:
*   **Cost-Efficiency:** Generally more cost-effective, especially at scale.
*   **Higher Throughput:** Designed for massive data ingestion rates.
*   **Exactly-Once Semantics:** Crucially, it supports exactly-once delivery within a stream, eliminating the need for client-side deduplication.
*   **Schema Evolution:** Better handling of schema updates (e.g., adding nullable columns).
*   **Type Safety:** Uses Avro or Protobuf for data serialization, offering stronger type checking than raw JSON. While the API supports JSON payload, using Avro/Protobuf is recommended for optimal performance and schema validation. For simplicity in this article, we'll focus on the JSON stream format which is easier to integrate with typical HTTP services.
*   **Offset-based Replay:** Enables reliable recovery from transient errors.

### The JSON Stream Format

When using the Storage Write API with JSON, data is sent as a list of JSON objects within the `json_rows` field of an `AppendRowsRequest`. Each object represents a row. The API automatically maps these JSON fields to BigQuery table columns based on their names.

Example `AppendRowsRequest` payload (simplified for conceptual understanding):

```json
{
  "writeStream": "projects/my-project/datasets/my_dataset/tables/my_table/streams/my_stream_id",
  "offset": {
    "value": "123"
  },
  "jsonRows": {
    "rows": [
      {"event_id": "abc-123", "event_timestamp": "2023-10-27T10:00:00Z", "payload": {"user_id": 123, "action": "click"}},
      {"event_id": "def-456", "event_timestamp": "2023-10-27T10:00:01Z", "payload": {"user_id": 456, "action": "view"}}
    ]
  }
}
```

### Append-Rows Stream Naming Rules

The Storage Write API uses streams to manage data ingestion. There are two primary types of streams, differentiated by their naming conventions and guarantees:

1.  **`_default` stream:** This is the default, unbuffered stream. It provides **at-most-once** semantics. Each `AppendRowsRequest` immediately writes data to BigQuery. If a request fails, the data is lost unless the client retries. There's no built-in deduplication. This is generally not recommended for mission-critical data.
2.  **`_append_` streams (e.g., `_append_stream_id`):** These are *buffered* streams that provide **exactly-once** semantics. When you create a stream with a custom ID starting with `_append_`, the API buffers data internally. You must explicitly call `WriteStream.Finalize()` and `WriteStream.Commit()` to make the data visible. The key advantage is that you can specify an `offset` in your `AppendRowsRequest`. If a request fails, you can retry it with the *same offset*, and the API will ensure the data is written exactly once. This is the recommended approach for reliable ingestion.

For this article, we focus on `_append_` streams due to their superior reliability and exactly-once guarantees.

### Offset-Based Replay and Exactly-Once Semantics

The `offset` field in `AppendRowsRequest` is fundamental to exactly-once delivery. When you append rows to an `_append_` stream, you provide an expected `offset`. The BigQuery service responds with the actual `offset` of the first row written in the `AppendRowsResponse`.

*   **Client Responsibility:** The client must maintain the current `offset` for each stream. When sending a batch of rows, the `offset` should be the number of rows successfully written *before* the current batch.
*   **Retry Mechanism:** If an `AppendRowsRequest` fails (e.g., network error, transient BigQuery error), the client can safely retry the *entire batch* with the *same offset*. The Storage Write API will detect if the data for that offset has already been written and will simply acknowledge it, preventing duplicates.
*   **Stream Finalization & Commitment:** For `_append_` streams, data is only visible for querying *after* the stream is finalized and committed. This allows you to group multiple `AppendRowsRequest` calls into a single atomic transaction.

### Client Libraries

Google Cloud provides idiomatic client libraries for the Storage Write API in several languages:
*   **Go:** `cloud.google.com/go/bigquery/storage/apiv1`
*   **Java:** `com.google.cloud:google-cloud-bigquery-storage`
*   **Python:** `google-cloud-bigquery-storage`
*   **Node.js:** `@google-cloud/bigquery-storage`

These libraries abstract away much of the gRPC complexity, providing higher-level APIs for stream management and data appending.

### Real Code Example (Python)

This Python example demonstrates how to use the BigQuery Storage Write API to create an `_append_` stream and append rows.

```python
import json
import time
from google.cloud import bigquery_storage_v1
from google.cloud.bigquery_storage_v1 import types
from google.cloud.bigquery_storage_v1 import writer

def append_rows_to_bq_stream(
    project_id: str,
    dataset_id: str,
    table_id: str,
    rows: list[dict] # List of dictionaries, each representing a row
):
    """Appends rows to a BigQuery table using the Storage Write API."""

    client = bigquery_storage_v1.BigQueryWriteClient()
    table_path = client.table_path(project_id, dataset_id, table_id)

    # Create a write stream.
    # Use the 'PENDING' type for exactly-once semantics and explicit commit.
    write_stream = types.WriteStream(type_=types.WriteStream.Type.PENDING)
    write_stream = client.create_write_stream(
        parent=table_path, write_stream=write_stream
    )
    stream_name = write_stream.name
    print(f"Created write stream: {stream_name}")

    # Create a JSON stream writer.
    # This writer manages the connection and sends batches.
    # The `offset` is managed internally by the writer for exactly-once delivery.
    json_stream_writer = writer.JsonStreamWriter(
        client,
        stream_name,
        # The schema of the table. The Storage Write API uses this to validate
        # and correctly parse JSON rows.
        # It's crucial to provide the correct schema.
        table_schema={
            "fields": [
                {"name": "event_id", "type": "STRING", "mode": "REQUIRED"},
                {"name": "event_timestamp", "type": "TIMESTAMP", "mode": "REQUIRED"},
                {"name": "user_id", "type": "INTEGER", "mode": "NULLABLE"},
                {"name": "action", "type": "STRING", "mode": "NULLABLE"},
                {"name": "payload", "type": "JSON", "mode": "NULLABLE"}
            ]
        }
    )

    # Append rows. The writer handles batching and sending.
    # It also manages the offset for exactly-once semantics.
    try:
        # The `append_rows` method returns a future.
        # We wait for it to complete to ensure the write is acknowledged.
        # In a real application, you might manage these futures asynchronously.
        append_future = json_stream_writer.append_rows(rows)
        response = append_future.result() # Blocks until response is received

        if response.row_errors:
            print(f"Row errors encountered: {response.row_errors}")
        else:
            print(f"Successfully appended {len(rows)} rows to stream {stream_name} at offset {response.append_result.offset.value}")

    except Exception as e:
        print(f"Error appending rows: {e}")
        # In a real system, you'd handle this more robustly,
        # potentially retrying or sending to a DLQ.
        client.batch_finalize_write_stream(names=[stream_name]) # Finalize to release resources
        raise

    finally:
        # Finalize the stream. This makes the buffered data visible.
        # For PENDING streams, data is only visible after commit.
        # For COMMITTED streams (not used here), data is visible immediately.
        client.finalize_write_stream(name=stream_name)
        print(f"Finalized write stream: {stream_name}")

        # Commit the stream. This is required for PENDING streams
        # to make the data permanent.
        batch_commit_write_streams_request = types.BatchCommitWriteStreamsRequest()
        batch_commit_write_streams_request.parent = table_path
        batch_commit_write_streams_request.write_streams.append(stream_name)
        client.batch_commit_write_streams(batch_commit_write_streams_request)
        print(f"Committed write stream: {stream_name}")

# Example usage:
if __name__ == "__main__":
    PROJECT_ID = "your-gcp-project-id"
    DATASET_ID = "your_dataset"
    TABLE_ID = "your_table"

    sample_rows = [
        {"event_id": "uuid-1", "event_timestamp": "2023-10-27T10:00:00.123456Z", "user_id": 1, "action": "login", "payload": {"ip": "1.1.1.1"}},
        {"event_id": "uuid-2", "event_timestamp": "2023-10-27T10:00:01.678901Z", "user_id": 2, "action": "logout", "payload": {"duration_s": 600}},
    ]

    # Ensure the table and dataset exist before running this.
    # The table schema should match the fields provided to JsonStreamWriter.
    append_rows_to_bq_stream(PROJECT_ID, DATASET_ID, TABLE_ID, sample_rows)

```

**Key Takeaways from the Code:**
*   **`WriteStream.Type.PENDING`:** This is crucial for exactly-once semantics. Data is buffered and only made visible after explicit `finalize_write_stream` and `batch_commit_write_streams`.
*   **`JsonStreamWriter`:** This helper class simplifies managing the stream, batching rows, and handling offsets.
*   **Schema Definition:** Providing `table_schema` to `JsonStreamWriter` is vital for correct parsing and validation of JSON rows.
*   **Error Handling:** The `try...except...finally` block demonstrates how to handle potential errors during appending and ensures streams are finalized/committed. In production, you'd implement more sophisticated retry logic and potentially a Dead Letter Queue (DLQ) for unrecoverable errors.

## 3. Partitioning and Clustering: Optimizing BigQuery

BigQuery's power lies in its ability to scan massive datasets quickly. Partitioning and clustering are fundamental techniques to optimize query performance and reduce costs by minimizing the amount of data scanned.

### Partitioning: Segmenting Data

Partitioning divides a table into smaller, more manageable segments based on the value of a specific column or ingestion time. Queries that filter on the partitioning column will only scan relevant partitions, significantly reducing data processed.

1.  **Ingestion-time Partitioning:**
    *   **Mechanism:** BigQuery automatically partitions data based on the time it is ingested into the table.
    *   **Pseudo-columns:** Uses `_PARTITIONTIME` (TIMESTAMP) or `_PARTITIONDATE` (DATE) pseudo-columns.
    *   **Use Case:** Ideal when event time is not available or reliable, or when you primarily query data based on when it arrived in BigQuery.
    *   **Example:** `PARTITION BY _PARTITIONDATE`

2.  **Event-time Partitioning (Column-based):**
    *   **Mechanism:** Partitions data based on a `TIMESTAMP` or `DATE` column within your table schema. This is the most common and recommended approach for event data.
    *   **Use Case:** When you have a reliable event timestamp (e.g., `event_timestamp`, `created_at`) that accurately reflects when the event occurred. This allows queries to align with business logic timeframes.
    *   **Example:** `PARTITION BY event_timestamp`

### Clustering: Sorting Data Within Partitions

Clustering sorts data within each partition based on the values of one or more specified columns. When queries filter or aggregate on these clustered columns, BigQuery can efficiently prune blocks of data that don't match the filter, further reducing scanned bytes.

*   **Mechanism:** You specify up to four clustering columns. BigQuery physically co-locates rows with similar values in these columns.
*   **Why Clustering Beats Partitioning for Some Filter Shapes:** Partitioning is effective for broad time-based filters. However, if you need to filter on a high-cardinality column *within* a specific time range (e.g., `user_id` or `device_id`), clustering shines. A query like `SELECT * FROM my_table WHERE _PARTITIONDATE = '2023-10-27' AND user_id = 123` will benefit immensely from both partitioning on `_PARTITIONDATE` and clustering on `user_id`.
*   **Integer-range Clustering:** BigQuery supports clustering on `INTEGER` columns. For example, if you have `user_id` as an `INTEGER`, clustering on it will group users together.

### Partition Expiration

Partition expiration automatically deletes old partitions after a specified duration. This is crucial for managing data lifecycle, complying with retention policies, and controlling storage costs.

*   **Mechanism:** You set a `partition_expiration_days` (or `partition_expiration_microseconds`) property when creating or updating a table.
*   **Benefit:** Reduces long-term storage costs and simplifies data retention management.

### Cost/Latency Trade-offs

*   **Reduced Cost:** Both partitioning and clustering reduce the amount of data BigQuery has to scan for many queries, directly translating to lower query costs (BigQuery charges for scanned data).
*   **Improved Latency:** Less data scanned means faster query execution times.
*   **Ingestion Overhead:** There's a minor overhead for BigQuery to maintain partitions and clusters, but this is negligible compared to the query cost and performance benefits.
*   **Small Partitions:** Avoid creating too many very small partitions, as this can sometimes lead to metadata overhead. BigQuery handles this fairly well, but it's a consideration.

### DDL Example

Here's a `CREATE TABLE` statement demonstrating event-time partitioning and clustering:

```sql
CREATE TABLE `your-gcp-project-id.your_dataset.your_table`
(
    event_id STRING NOT NULL OPTIONS(description="Unique identifier for the event"),
    event_timestamp TIMESTAMP NOT NULL OPTIONS(description="Timestamp when the event occurred"),
    user_id INTEGER OPTIONS(description="Identifier for the user"),
    session_id STRING OPTIONS(description="Identifier for the user session"),
    action STRING OPTIONS(description="Type of action performed"),
    payload JSON OPTIONS(description="JSON payload containing additional event details")
)
PARTITION BY DATE(event_timestamp) -- Partition by the date component of event_timestamp
CLUSTER BY user_id, session_id      -- Cluster within each partition by user_id and session_id
OPTIONS(
    description="Table for storing application events, partitioned by event date and clustered by user/session.",
    partition_expiration_days=90, -- Partitions older than 90 days will be automatically deleted
    require_partition_filter=true -- Enforce partition filtering in queries to prevent full table scans
);
```

**Explanation:**
*   `PARTITION BY DATE(event_timestamp)`: Uses the `event_timestamp` column to partition the table by day.
*   `CLUSTER BY user_id, session_id`: Within each daily partition, data will be sorted and grouped by `user_id` and then `session_id`.
*   `partition_expiration_days=90`: Any partition older than 90 days from its creation will be automatically removed.
*   `require_partition_filter=true`: This is a critical option for cost control. It forces users to include a filter on `_PARTITIONTIME` (or `event_timestamp` in this case) in their queries, preventing accidental full table scans.

## 4. A FastAPI Async Receiver: The Ingestion Gateway

The Cloud Run receiver acts as the HTTP endpoint for our ingestion pipeline. FastAPI, with its async capabilities and Pydantic for data validation, is an excellent choice for building this service.

### FastAPI Plus Async Context Managers

FastAPI naturally supports `async`/`await`, which is crucial for I/O-bound operations like writing to BigQuery. The `google-cloud-bigquery-storage` Python client library, however, is primarily synchronous. To use it efficiently in an async FastAPI application, we need to offload synchronous BigQuery calls to a thread pool or use `asyncio.to_thread`. More importantly, managing the `BigQueryWriteClient` and its underlying gRPC streams requires careful handling, especially for connection pooling and graceful shutdown.

Async context managers (`async with`) are ideal for this. They allow us to manage the lifecycle of BigQuery write streams, ensuring they are properly initialized and closed.

### Connection Pooling

Creating a new `BigQueryWriteClient` and a new write stream for every incoming request is inefficient. It incurs connection setup overhead and doesn't leverage existing connections. A better approach is to:
1.  **Reuse `BigQueryWriteClient`:** The `BigQueryWriteClient` itself can be a singleton or created once per process.
2.  **Pool Write Streams:** For `_append_` streams, you can create a pool of long-lived streams. Each stream can handle multiple `AppendRowsRequest` calls. When a request comes in, it picks an available stream from the pool, appends rows, and releases the stream back to the pool. This minimizes stream creation/finalization overhead. For simplicity in the example, we'll create a stream per batch, but a more advanced approach would involve pooling.

### Backpressure

Handling backpressure is critical when your ingestion rate exceeds your processing capacity or BigQuery's write limits.
*   **Internal Queues:** FastAPI can use internal queues (e.g., `asyncio.Queue`) to buffer incoming requests before processing. If the queue fills up, new requests can be rejected with a `503 Service Unavailable`.
*   **Cloud Run Auto-scaling:** Cloud Run automatically scales instances, which helps. However, if a single instance is overwhelmed, internal queues provide a buffer.
*   **BigQuery Quotas:** BigQuery has quotas on streaming inserts. If you hit these, the Storage Write API client will typically retry, but sustained quota breaches require intervention (e.g., increasing quotas or throttling upstream).

### Graceful Shutdown of In-flight Streams

When a Cloud Run instance is terminated (e.g., scaling down, deployment), it receives a `SIGTERM` signal. The application needs to handle this gracefully:
1.  **Stop accepting new requests.**
2.  **Process existing in-flight requests:** Allow current `AppendRowsRequest` calls to complete.
3.  **Finalize and commit any open `_append_` streams:** This ensures all buffered data is flushed to BigQuery. If not done, data in pending streams might be lost or delayed.

FastAPI's ` lifespan ` event handler is perfect for this.

### Cloud Run Concurrency Tuning

Cloud Run offers several parameters to optimize performance and cost:
*   **`concurrency`:** The maximum number of concurrent requests an instance can handle. A higher concurrency (e.g., 80-250) is generally good for I/O-bound services like our receiver, as long as your application is truly async and doesn't block.
*   **`request timeouts`:** Set this high enough to accommodate BigQuery write latencies, especially for large batches, but not so high that failed requests linger. 60-120 seconds is a reasonable starting point.
*   **`min-instances` / `max-instances`:** `min-instances` keeps a baseline number of instances warm, reducing cold start latency. `max-instances` caps your spending and resource usage.
*   **Streaming vs. Buffered Responses:** For the ingestion receiver, we are primarily *receiving* data, not *streaming responses* back. The focus is on efficiently processing the incoming request body.

### Idempotency Keys

Client-side retries are common. Without idempotency, a retried request could lead to duplicate data in BigQuery.
*   **Mechanism:** The client sends a unique `Idempotency-Key` header with each request.
*   **Receiver Logic:**
    1.  Upon receiving a request, check if the `Idempotency-Key` has been seen recently (e.g., in a Redis cache or a small in-memory cache).
    2.  If seen and still "processing", return a `202 Accepted` or `409 Conflict` (depending on desired behavior) without re-processing.
    3.  If seen and "processed successfully", return a `200 OK` without re-processing.
    4.  If not seen, process the request, store the `Idempotency-Key` with its status, and return the result.
*   **BigQuery Storage Write API and Idempotency:** The Storage Write API's offset-based replay provides idempotency *within a single stream*. However, application-level idempotency keys protect against duplicates if the *entire request to Cloud Run* is retried before the BigQuery write even starts or if a new stream is created. It's a complementary layer of protection.

### Real Code Example (FastAPI)

This example shows a FastAPI receiver with a singleton BigQuery client, handling incoming JSON events, and writing them using the Storage Write API.

```python
import os
import asyncio
import logging
from contextlib import asynccontextmanager
from typing import List, Dict, Any, Optional

from fastapi import FastAPI, Request, HTTPException, status
from pydantic import BaseModel, Field
from google.cloud import bigquery_storage_v1
from google.cloud.bigquery_storage_v1 import types
from google.cloud.bigquery_storage_v1 import writer
from concurrent.futures import ThreadPoolExecutor

# --- Configuration ---
PROJECT_ID = os.environ.get("GCP_PROJECT_ID")
DATASET_ID = os.environ.get("BQ_DATASET_ID")
TABLE_ID = os.environ.get("BQ_TABLE_ID")
BIGQUERY_TABLE_SCHEMA = {
    "fields": [
        {"name": "event_id", "type": "STRING", "mode": "REQUIRED"},
        {"name": "event_timestamp", "type": "TIMESTAMP", "mode": "REQUIRED"},
        {"name": "user_id", "type": "INTEGER", "mode": "NULLABLE"},
        {"name": "action", "type": "STRING", "mode": "NULLABLE"},
        {"name": "payload", "type": "JSON", "mode": "NULLABLE"}
    ]
}
MAX_BIGQUERY_STREAM_IDLE_SECONDS = 300 # Close streams if idle for too long
MAX_BIGQUERY_STREAM_BATCH_SIZE = 1000 # Max rows per append call
MAX_BIGQUERY_STREAM_BATCH_BYTES = 10 * 1024 * 1024 # 10MB per append call
MAX_WORKER_THREADS = 5 # For offloading synchronous BigQuery calls

# --- Logging ---
logging.basicConfig(level=logging.INFO)
logger = logging.getLogger(__name__)

# --- Global BigQuery Client and Thread Pool ---
# We use a global client and thread pool to reuse resources efficiently.
bq_storage_client: Optional[bigquery_storage_v1.BigQueryWriteClient] = None
bq_executor: Optional[ThreadPoolExecutor] = None

# --- Pydantic Models for Request Validation ---
class EventPayload(BaseModel):
    ip: Optional[str] = None
    duration_s: Optional[int] = None
    # Add other dynamic fields as needed. Use Any for truly flexible JSON.
    # For strict validation, define all expected fields.

class Event(BaseModel):
    event_id: str = Field(..., description="Unique identifier for the event")
    event_timestamp: str = Field(..., description="ISO 8601 timestamp of the event")
    user_id: Optional[int] = Field(None, description="User ID associated with the event")
    action: Optional[str] = Field(None, description="Action performed by the user")
    payload: Optional[EventPayload] = Field(None, description="Additional event details")

# --- FastAPI Lifespan Management ---
@asynccontextmanager
async def lifespan(app: FastAPI):
    global bq_storage_client, bq_executor
    logger.info("Starting up Cloud Run receiver...")

    if not all([PROJECT_ID, DATASET_ID, TABLE_ID]):
        logger.error("Missing required environment variables for BigQuery connection.")
        raise RuntimeError("BigQuery environment variables not set.")

    bq_storage_client = bigquery_storage_v1.BigQueryWriteClient()
    bq_executor = ThreadPoolExecutor(max_workers=MAX_WORKER_THREADS)
    logger.info("BigQueryWriteClient and ThreadPoolExecutor initialized.")

    yield # Application runs

    logger.info("Shutting down Cloud Run receiver...")
    if bq_storage_client:
        # In a real scenario, you'd manage open write streams here.
        # For this simple example, we assume streams are short-lived per request.
        # If using long-lived pooled streams, you'd finalize/commit them here.
        bq_storage_client.transport.close() # Close gRPC connections
        logger.info("BigQueryWriteClient closed.")
    if bq_executor:
        bq_executor.shutdown(wait=True)
        logger.info("ThreadPoolExecutor shut down.")
    logger.info("Cloud Run receiver shut down complete.")

app = FastAPI(
    title="BigQuery Serverless Ingestion Receiver",
    description="Receives events and streams them to BigQuery via Storage Write API.",
    version="1.0.0",
    lifespan=lifespan
)

# --- Idempotency Cache (In-memory for simplicity, use Redis for production) ---
# This is a very basic in-memory cache. For production, use a distributed cache like Redis.
# Stores {idempotency_key: (status, timestamp)}
IDEMPOTENCY_CACHE: Dict[str, tuple[str, float]] = {}
IDEMPOTENCY_CACHE_EXPIRATION_SECONDS = 3600 # 1 hour

def check_idempotency(idempotency_key: str) -> Optional[str]:
    """Checks idempotency cache. Returns 'processed' if seen, None otherwise."""
    if idempotency_key in IDEMPOTENCY_CACHE:
        status, timestamp = IDEMPOTENCY_CACHE[idempotency_key]
        if time.time() - timestamp < IDEMPOTENCY_CACHE_EXPIRATION_SECONDS:
            logger.info(f"Idempotent request detected for key: {idempotency_key}. Status: {status}")
            return status
        else:
            # Expired entry, remove it
            del IDEMPOTENCY_CACHE[idempotency_key]
    return None

def set_idempotency_status(idempotency_key: str, status: str):
    """Sets idempotency status."""
    IDEMPOTENCY_CACHE[idempotency_key] = (status, time.time())

# --- BigQuery Write Function (Synchronous, to be run in thread pool) ---
def _write_to_bigquery_sync(
    client: bigquery_storage_v1.BigQueryWriteClient,
    table_path: str,
    rows_to_insert: List[Dict[str, Any]]
):
    """Synchronously writes rows to BigQuery using Storage Write API."""
    write_stream = client.create_write_stream(
        parent=table_path, write_stream=types.WriteStream(type_=types.WriteStream.Type.PENDING)
    )
    stream_name = write_stream.name
    logger.info(f"Created write stream: {stream_name}")

    json_stream_writer = writer.JsonStreamWriter(
        client,
        stream_name,
        table_schema=BIGQUERY_TABLE_SCHEMA
    )

    try:
        append_future = json_stream_writer.append_rows(rows_to_insert)
        response = append_future.result() # Blocks until response

        if response.row_errors:
            logger.error(f"Row errors for stream {stream_name}: {response.row_errors}")
            raise RuntimeError(f"BigQuery row errors: {response.row_errors}")
        else:
            logger.info(f"Successfully appended {len(rows_to_insert)} rows to stream {stream_name} at offset {response.append_result.offset.value}")

    except Exception as e:
        logger.error(f"Failed to append rows to BigQuery stream {stream_name}: {e}")
        # Finalize to release resources even on error
        client.finalize_write_stream(name=stream_name)
        raise
    finally:
        # Finalize and commit the stream to make data visible
        client.finalize_write_stream(name=stream_name)
        commit_request = types.BatchCommitWriteStreamsRequest(
            parent=table_path,
            write_streams=[stream_name]
        )
        client.batch_commit_write_streams(commit_request)
        logger.info(f"Committed write stream: {stream_name}")


# --- FastAPI Endpoint ---
@app.post("/ingest")
async def ingest_events(request: Request, events: List[Event]):
    """
    Receives a batch of events and streams them to BigQuery.
    """
    idempotency_key = request.headers.get("Idempotency-Key")

    if idempotency_key:
        status_in_cache = check_idempotency(idempotency_key)
        if status_in_cache == "processed":
            return {"message": "Request already processed", "status": "idempotent_success"}
        elif status_in_cache == "processing":
            raise HTTPException(
                status_code=status.HTTP_409_CONFLICT,
                detail="Request with this Idempotency-Key is already being processed."
            )
        set_idempotency_status(idempotency_key, "processing")

    if not bq_storage_client or not bq_executor:
        logger.error("BigQuery client or executor not initialized.")
        raise HTTPException(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            detail="Service not ready."
        )

    table_path = bq_storage_client.table_path(PROJECT_ID, DATASET_ID, TABLE_ID)
    rows_to_insert = [event.model_dump(mode='json') for event in events]

    try:
        # Offload synchronous BigQuery write to a separate thread
        await asyncio.to_thread(
            _write_to_bigquery_sync,
            bq_storage_client,
            table_path,
            rows_to_insert
        )
        if idempotency_key:
            set_idempotency_status(idempotency_key, "processed")
        return {"message": f"Successfully ingested {len(events)} events."}
    except Exception as e:
        logger.error(f"Failed to ingest events: {e}", exc_info=True)
        if idempotency_key:
            set_idempotency_status(idempotency_key, "failed")
        raise HTTPException(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            detail=f"Failed to write to BigQuery: {e}"
        )
```

### Top Cost-Optimization Levers Ranked by Impact

1.  **BigQuery Partitioning & Clustering:** **Highest Impact.** Reduces query costs by minimizing scanned data. Crucial for any analytical workload. `require_partition_filter` is a must.
2.  **BigQuery Partition Expiration:** **High Impact.** Automatically deletes old data, directly reducing BigQuery storage costs. Align with data retention policies.
3.  **BigQuery Schema Optimization:** **High Impact.** Use appropriate data types (e.g., `INT64` instead of `STRING` for IDs, `DATE` instead of `TIMESTAMP` if time-of-day isn't needed). Avoid unnecessary columns. This reduces storage footprint and query scan costs.
4.  **Cloud Run Concurrency:** **Medium-High Impact.** High concurrency (if your app is truly async) allows fewer instances to handle more requests, reducing overall CPU/memory consumption and idle costs.
5.  **Cloud Run `min-instances`:** **Medium Impact.** Setting `min-instances=0` when cold starts are acceptable for non-critical pipelines saves idle costs. For critical, low-latency ingestion, a small `min-instances` is often justified.
6.  **Batching for BigQuery Storage Write API:** **Medium Impact.** Sending larger batches of rows per `AppendRowsRequest` reduces the number of gRPC calls and associated overhead, potentially improving throughput and efficiency. Avoid very small batches.
7.  **Pub/Sub Message Retention:** **Low-Medium Impact.** Keep message retention duration as short as necessary (default 7 days is usually fine). Only extend for specific recovery needs, as longer retention incurs storage costs.

## 7. Observability, Failure Modes, and Production Hardening

Building a production pipeline requires more than just code; it needs robust operational practices.

### Dead Letter Queues (DLQs)

DLQs are essential for isolating and managing messages that cannot be processed successfully.
*   **Pub/Sub DLQ:** If using Pub/Sub as the event source, configure a DLQ on the subscription. Messages that fail `max_delivery_attempts` are automatically forwarded.
*   **Cloud Run Application DLQ:** If Cloud Run receives direct HTTP requests, or if internal processing errors occur *before* BigQuery, the application itself should log the failed event and, ideally, publish it to a separate Pub/Sub DLQ topic.
*   **Handling DLQ Messages:** Set up a separate process (e.g., a Cloud Function, Cloud Run Job) to consume from the DLQ, analyze failures, correct data (if possible), and re-ingest or archive. This prevents poison messages from blocking the main pipeline.

### Schema Drift Handling

Data schemas evolve. Your pipeline must be resilient to these changes.
*   **BigQuery's Flexible Schema:** BigQuery is schema-on-read. You can add new nullable columns to an existing table without breaking existing queries or requiring downtime.
*   **Application-level Validation:** Pydantic models in FastAPI provide strict schema validation.
    *   **Strict Mode:** If an incoming field is not in the Pydantic model, it's rejected. Good for enforcing strict contracts.
    *   **Flexible Mode:** Use `extra='allow'` in Pydantic or `Dict[str, Any]` to allow unknown fields, which can then be stored in a `JSON` type column in BigQuery. This is often preferred for event data.
*   **Schema Evolution Strategy:**
    1.  **Backward Compatible Changes:** Add new nullable fields to BigQuery table schema. Update Pydantic model to include new fields (making them `Optional`).
    2.  **Breaking Changes (e.g., renaming, type changes):** Avoid if possible. If necessary, create a new table, migrate data, and switch the ingestion target.
    3.  **Invalid/Malformed Data:** Store in a separate "quarantine" table or push to a specific DLQ for manual inspection.

### Poison Messages

A poison message is one that consistently causes processing failures, even after retries.
*   **DLQ Mechanism:** Pub/Sub's DLQ and application-level DLQs are the primary defense. After a configurable number of retries, the message is moved, preventing it from indefinitely blocking the main processing queue.
*   **Monitoring & Alerting:** Monitor DLQ size. A growing DLQ indicates a poison message problem or a systemic issue.
*   **Analysis:** Inspect poison messages to understand the root cause (e.g., invalid JSON, unexpected data types, application bug).

### Quotas and Retry Semantics with Exponential Backoff

GCP services have quotas. Exceeding them results in `RESOURCE_EXHAUSTED` errors.
*   **BigQuery Storage Write API Quotas:** QPS limits per project/region.
*   **Cloud Run Quotas:** Instance limits, CPU limits.
*   **Retry Logic:** Your client (the Cloud Run receiver) must implement robust retry logic with **exponential backoff and jitter**.
    *   **Exponential Backoff:** Increase delay between retries exponentially (e.g., 1s, 2s, 4s, 8s...).
    *   **Jitter:** Add a small random delay to prevent thundering herd problems when many clients retry simultaneously.
    *   **Max Retries:** Define a maximum number of retries before failing the request and sending it to a DLQ.
    *   **Client Libraries:** Google Cloud client libraries often have built-in retry mechanisms, but verify their configuration.

### Alerting and SLOs

Define Service Level Objectives (SLOs) and set up alerts to proactively detect issues.
*   **Key Metrics (Cloud Monitoring):**
    *   **Cloud Run:**
        *   Request latency (p99, p95)
        *   Error rates (5xx HTTP responses)
        *   Request count
        *   CPU utilization, Memory utilization
        *   Instance count
    *   **BigQuery:**
        *   Storage Write API `append_rows` latency
        *   Storage Write API `append_rows` error count
        *   Data volume ingested
        *   Table storage size
    *   **Pub/Sub (if used):**
        *   Undelivered message count (backlog size)
        *   Oldest unacknowledged message age
        *   DLQ message count
*   **SLOs:**
    *   **Availability:** Ingestion endpoint available 99.9% of the time (e.g., < 0.1% 5xx errors).
    *   **Latency:** P99 ingestion latency < 5 seconds.
    *   **Throughput:** Successfully ingest X events per second.
    *   **Data Freshness:** Data visible in BigQuery within Y minutes of event occurrence.
*   **Alerting:** Configure alerts in Cloud Monitoring (or your preferred alerting system) when SLOs are violated. Route alerts to on-call engineers.

### Runbook-Style Failure Table

A runbook provides clear, actionable steps for common failure scenarios.

| Failure Scenario             | Symptoms                                     | Troubleshooting Steps                                                | Resolution                                                                   |
| :--------------------------- | :------------------------------------------- | :------------------------------------------------------------------- | :--------------------------------------------------------------------------- |
| **Cloud Run 5xx Errors**     | Increased 5xx rate, high latency, instance crash | Check Cloud Run logs for exceptions. Monitor CPU/Memory utilization. | Investigate code errors. Increase `CPU`/`Memory` limits. Adjust `concurrency`. |
| **Cloud Run Hitting Max Instances** | `max_instances` reached, requests queued/dropped | Check request rate vs. processing capacity. Monitor `concurrency`.   | Increase `max_instances` (if budget allows). Optimize code for faster processing. |
| **BigQuery Write Failures**  | `BigQueryWriteClient` errors, data gaps in BQ | Check BigQuery Storage Write API quotas. Check table schema.         | Request quota increase. Correct application schema. Retry failed batches from DLQ. |
| **Pub/Sub DLQ Backlog Growing** | `dlq-events-topic` message count increasing | Inspect messages in DLQ. Check ingestion app logs for common errors. | Identify poison message cause. Deploy fix. Re-process DLQ messages.          |
| **Data Not Appearing in BQ** | Empty/stale tables, `SELECT COUNT(*)` low     | Check Cloud Run logs for `_write_to_bigquery_sync` success/failure. Verify stream commit. | Ensure `finalize_write_stream` and `batch_commit_write_streams` are called. |
| **High BigQuery Query Costs**| Cost alerts for BigQuery query usage.         | Analyze query patterns. Check if partitioning/clustering are used.   | Enforce `require_partition_filter`. Optimize queries. Review schema.         |

## 8. Production Checklist and Conclusion

Before pushing your serverless ingestion pipeline to production, ensure you've addressed these critical aspects:

### Production Checklist

*   [ ] **IAM:** Least-privilege service accounts configured for all components.
*   [ ] **Networking:** VPC Service Controls (if required for security boundaries).
*   [ ] **Monitoring & Alerting:** Comprehensive dashboards and alerts for all key metrics and SLOs.
*   [ ] **Logging:** Structured logging implemented in the Cloud Run application, ingested by Cloud Logging.
*   [ ] **Error Handling:** Robust retry logic with exponential backoff and jitter. Dead Letter Queues (DLQs) configured and monitored.
*   [ ] **Schema Management:** Clear strategy for handling schema evolution and validation.
*   [ ] **Idempotency:** Application-level idempotency keys implemented for client retries.
*   [ ] **Security:** Secrets managed securely (e.g., Secret Manager). No sensitive data in logs.
*   [ ] **Cost Management:** Budget alerts configured. Regular review of cost drivers.
*   [ ] **Performance Testing:** Load testing performed to validate scalability and identify bottlenecks.
*   [ ] **Graceful Shutdown:** Cloud Run application handles `SIGTERM` to finalize in-flight BigQuery streams.
*   [ ] **Terraform:** All infrastructure defined in Terraform, reviewed, and version-controlled. `deletion_protection` enabled for critical resources.
*   [ ] **Documentation:** Runbooks, architectural diagrams, and schema definitions are up-to-date.

### Conclusion and Key Trade-offs

Building a serverless data ingestion pipeline with BigQuery and Cloud Run offers immense benefits:
*   **Scalability:** Automatically scales to handle fluctuating loads without manual intervention.
*   **Reliability:** Leverages Pub/Sub's buffering, BigQuery Storage Write API's exactly-once semantics, and robust error handling.
*   **Cost-Effectiveness:** Pay-per-use model, optimized by efficient resource utilization and BigQuery's storage/query optimizations.
*   **Reduced Operational Overhead:** No servers to manage, patch, or upgrade.

However, this approach also involves trade-offs:

*   **Complexity of Distributed Systems:** While serverless abstracts away infrastructure, managing distributed state, eventual consistency, and complex error scenarios still requires careful design.
*   **Vendor Lock-in:** Deep integration with GCP services can make migration to other clouds more challenging.
*   **Observability Challenges:** Debugging distributed systems can be harder than monolithic applications, requiring good tracing and structured logging.
*   **Cost Visibility:** While cost-effective, understanding and predicting costs can be tricky without careful monitoring and analysis of usage patterns.
*   **Cold Starts:** Though mitigated by `min-instances`, serverless functions can experience latency spikes during cold starts if not managed.

By carefully considering these aspects and implementing the detailed strategies outlined in this article, you can build a highly effective, production-grade serverless data ingestion pipeline that reliably fuels your data analytics and machine learning initiatives. This architecture is a cornerstone for modern data platforms, enabling rapid iteration and scalable data-driven decision-making.
