# Kubernetes Operators and custom resources

Kubernetes is excellent at managing stateless applications. If a stateless pod dies, a ReplicaSet can simply spin up a new one. However, managing complex stateful applications—like databases, message queues, or specialized monitoring systems—requires domain-specific knowledge that Kubernetes doesn't possess out of the box.

This is where the Operator pattern shines.

## What is an Operator?
An Operator is a method of packaging, deploying, and managing a Kubernetes application. It takes human operational knowledge (e.g., how to back up a database, how to upgrade a cluster without downtime, how to handle failover) and encodes it into software that runs natively within the Kubernetes control plane.

## Custom Resource Definitions (CRDs)
Operators rely heavily on Custom Resource Definitions (CRDs). A CRD extends the Kubernetes API, allowing developers to define new resource types. Instead of just managing `Pods` and `Services`, an operator might manage a `PostgresCluster` or a `KafkaTopic` resource.

The Operator continuously watches these custom resources. When a user submits a declarative configuration for a `PostgresCluster`, the Operator's control loop acts to reconcile the current state of the cluster with the desired state specified in the CRD. This brings the declarative power of Kubernetes to any complex, stateful workload.
