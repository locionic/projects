Kubernetes' default deployment strategy, `RollingUpdate`, is adequate for small services, but dangerous for mission-critical production systems:

1. **Unbounded Blast Radius:** If a new container image contains a subtle runtime panic or memory leak, `RollingUpdate` will steadily replace 100% of healthy pods until all instances are degraded.
2. **No Metric-Driven Rollbacks:** Kubernetes only checks container readiness/liveness HTTP probes. If your API returns HTTP 200 with an empty JSON payload or throws internal 500 errors on 3% of requests, Kubernetes considers the pod "healthy" and continues rolling out.
3. **No Preview Validation:** You cannot run sanity or smoke tests against the new version in production before routing live user traffic to it.

To solve this, advanced engineering teams use **Blue-Green Deployments** or **Canary Releases with Automated Metric Analysis**.

## 1. RollingUpdate vs Blue-Green vs Canary

| Dimension | RollingUpdate (Default) | Blue-Green Deployment | Canary Release |
|---|---|---|---|
| **Traffic Shift** | Incremental pod replacement | Instant 0% to 100% switch | Progressive (e.g. 5% $\to$ 20% $\to$ 100%) |
| **Blast Radius** | 100% of users over time | 100% of users immediately | Isolated to small sample (e.g. 5%) |
| **Resource Overhead** | +25% max surge capacity | +100% (2x full clusters/replicas) | +10%–20% canary pods |
| **Rollback Speed** | Slow (reverse RollingUpdate) | Instant (flip router back to Blue) | Instant (drop canary traffic to 0%) |
| **Metric Gate** | Basic Liveness/Readiness probe | Manual or scripted smoke test | Automated Prometheus/Datadog queries |

## 2. Blue-Green Deployments: The Instant Cutover Pattern

In Blue-Green, two identical environments exist simultaneously:
* **Blue (Active):** Serves 100% of production traffic.
* **Green (Preview):** Deploys the new version. Internal developers run smoke tests against `preview.example.com`.

```
                       User Ingress / Load Balancer
                                     │
                      [ Active Service Selector ]
                                     │
                     ┌───────────────┴───────────────┐
                     ▼ (100% traffic)                ▼ (0% traffic)
              [ Blue Pods v1.2 ]              [ Green Pods v1.3 ]
```

When tests pass, the service selector flips from `version: v1.2` to `version: v1.3`. If a catastrophic failure occurs post-switch, flip the service selector back to Blue instantaneously.

### The Golden Rule of Blue-Green: Database Expand/Contract

Because Blue and Green run simultaneously during the cutover window, your database **must support both versions at the exact same time**:

```
Step 1 (Expand): Add nullable column or new table. Deploy DB migration.
Step 2 (Deploy): Green version uses new column, Blue version ignores it.
Step 3 (Cutover): Route traffic to Green.
Step 4 (Contract): Drop old deprecated columns after Blue is destroyed.
```

## 3. Canary Releases with Argo Rollouts: Progressive Traffic Shifting

[Argo Rollouts](https://argoproj.github.io/argo-rollouts/) replaces the standard Kubernetes `Deployment` object with a `Rollout` Custom Resource, providing automated Canary steps and Prometheus metric analysis.

```
Incoming Traffic ───► Ingress / Service Mesh (Istio / NGINX / ALB)
                            │
            ┌───────────────┴───────────────┐
            ▼ (95% Live Traffic)            ▼ (5% Canary Traffic)
     [ Stable Service ]              [ Canary Service ]
            │                               │
     [ Stable Pods v1 ]              [ Canary Pods v2 ]
                                            │
                                            ▼
                                [ Prometheus Query Engine ]
                           (Error rate < 0.5%, p99 latency < 200ms)
                                     │              │
                              [ PASS: +20% ]   [ FAIL: Abort & Rollback ]
```

### Complete Production `Rollout` Manifest

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: payments-api
  namespace: production
spec:
  replicas: 10
  revisionHistoryLimit: 5
  selector:
    matchLabels:
      app: payments-api
  template:
    metadata:
      labels:
        app: payments-api
    spec:
      containers:
        - name: payments-api
          image: ghcr.io/my-org/payments-api:v2.4.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 500m
              memory: 512Mi
  strategy:
    canary:
      canaryService: payments-api-canary
      stableService: payments-api-stable
      trafficRouting:
        nginx:
          stableIngress: payments-api-ingress
      steps:
        # Step 1: Route 5% traffic to canary and pause 10 minutes
        - setWeight: 5
        - pause: { duration: 10m }
        # Step 2: Run automated Prometheus analysis
        - analysis:
            templates:
              - templateName: http-error-rate-check
        # Step 3: Increase traffic to 20%
        - setWeight: 20
        - pause: { duration: 30m }
        # Step 4: Increase traffic to 50%
        - setWeight: 50
        - pause: { duration: 15m }
```

## 4. Automated Metric Analysis with Prometheus

Instead of having on-call engineers watch Grafana dashboards during deploys, configure an `AnalysisTemplate` to evaluate your Service Level Objectives (SLOs) automatically:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: http-error-rate-check
  namespace: production
spec:
  metrics:
    - name: success-rate
      interval: 1m
      successCondition: result[0] >= 0.995 # Must maintain 99.5% success rate
      failureLimit: 3                      # Abort after 3 consecutive failed probes
      provider:
        prometheus:
          address: http://prometheus-k8s.monitoring:9090
          query: |
            sum(rate(http_requests_total{app="payments-api", status=~"2..|3.."}[2m]))
            /
            sum(rate(http_requests_total{app="payments-api"}[2m]))

    - name: p99-latency
      interval: 1m
      successCondition: result[0] <= 0.250 # Latency must stay under 250ms
      failureLimit: 2
      provider:
        prometheus:
          address: http://prometheus-k8s.monitoring:9090
          query: |
            histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{app="payments-api"}[2m])) by (le))
```

### What Happens When a Canary Fails?

If the new image throws 500 errors on the 5% canary slice:
1. The Prometheus query returns `success-rate < 0.995`.
2. Argo Rollouts detects 3 consecutive metric failures.
3. **Instant Auto-Rollback:** Traffic weight is immediately reset to 0% on the canary service.
4. The canary pods are terminated.
5. The Rollout status transitions to `Degraded`, firing a Slack alert to the engineering channel.
6. 95% of users never experienced the defect.

## 5. Summary Implementation Checklist

1. **Adopt Expand/Contract database migrations** so both old and new code versions run simultaneously without schema crashes.
2. **Define SLOs quantitatively** (p99 latency < X ms, 5xx error rate < Y%) before writing Canary analysis rules.
3. **Start with conservative canary weights:** 5% for 10 minutes $\to$ 20% for 30 minutes $\to$ 100%.
4. **Use Argo Rollouts or Flagger** with your existing Service Mesh (Istio/Linkerd) or Ingress (NGINX/Traefik) for dynamic header- and weight-based routing.
