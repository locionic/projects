As React applications scale, the folder structure transitions from being a matter of aesthetic preference to a critical architectural decision. With the introduction of the Next.js App Router, the paradigm shifted significantly. We moved away from the `pages/` directory—which often served as a catch-all for both routing and UI components—towards a more opinionated, convention-based routing system in the `app/` directory.

However, the App Router's flexibility, specifically its support for colocation, can easily lead to a chaotic codebase if not managed with a strict architectural philosophy. In this comprehensive guide, we will explore how to architect a highly scalable folder structure for Next.js App Router applications, drawing heavy inspiration from Feature-Sliced Design (FSD).

## The App Router Paradigm Shift

The Next.js App Router introduced Server Components by default, streaming, and nested layouts. The most significant structural change is **colocation**. In the `app/` directory, only files specifically named `page.tsx`, `layout.tsx`, `route.ts`, etc., are publicly accessible. 

This means you *can* place components, tests, and styles directly alongside your routes:

```text
app/
└── dashboard/
    ├── page.tsx
    ├── layout.tsx
    ├── DashboardGraph.tsx
    ├── dashboard.module.css
    └── dashboard.test.tsx
```

While this works for trivial applications, it breaks down quickly in enterprise environments. As the dashboard grows, the `app/dashboard` folder becomes a dumping ground for hundreds of files, violating the Single Responsibility Principle and making code navigation a nightmare.

## Enter Feature-Sliced Design (FSD)

Feature-Sliced Design is an architectural methodology for frontend projects. It enforces a strict hierarchy based on modularity and business domain. FSD divides a project into three main concepts: **Layers**, **Slices**, and **Segments**.

When adapting FSD for Next.js, we must respect the framework's native `app/` layer while organizing the rest of the application predictably. 

Here is the high-level architecture we recommend for scalable Next.js applications:

```text
src/
├── app/          # 1. Routing and entry points (Next.js native)
├── features/     # 2. Business value and user interactions
├── entities/     # 3. Business entities (User, Product, Order)
└── shared/       # 4. Reusable infrastructure and UI kit
```

Let's break down each layer and how it interacts with Next.js conventions.

### 1. The `app/` Layer: Pure Routing

The `app/` directory should be treated strictly as a routing and composition layer. It should contain minimal business logic. Its primary responsibilities are:
- Defining the route hierarchy.
- Fetching initial data for Server Components.
- Composing features and entities into pages.
- Handling global layouts, error boundaries, and loading states.

```tsx
// app/dashboard/page.tsx
import { DashboardWidget } from '@/features/dashboard-widget';
import { getUserProfile } from '@/entities/user';

export default async function DashboardPage() {
  const user = await getUserProfile();

  return (
    <main>
      <h1>Welcome back, {user.name}</h1>
      <DashboardWidget userId={user.id} />
    </main>
  );
}
```
Notice how the page acts as an orchestrator, delegating the actual UI and logic to the `features` and `entities` layers.

### 2. The `features/` Layer: User Scenarios

A feature is a piece of functionality that delivers business value. Examples include `auth-form`, `checkout-flow`, or `dashboard-widget`. Features are highly cohesive and can compose multiple entities.

Inside a feature, we divide the code into **Segments** (UI, model, api, lib):

```text
features/auth-form/
├── ui/                 # React components (e.g., LoginForm.tsx)
├── model/              # State management (Zustand, Redux, or React hooks)
├── api/                # Server Actions and API requests
└── index.ts            # Public API (Strict isolation)
```

In the context of the App Router, the `api/` segment is the perfect place to colocate your Next.js Server Actions:

```tsx
// features/auth-form/api/actions.ts
'use server'

import { signIn } from '@/shared/lib/auth';

export async function submitLogin(formData: FormData) {
  // Server action logic...
}
```

### 3. The `entities/` Layer: Business Domain

Entities represent the core domain models of your application. Unlike features, entities do not contain complex user scenarios. They provide the fundamental building blocks (types, UI components representing the entity, data fetching utilities).

For example, a `user` entity might look like this:

```text
entities/user/
├── ui/
│   ├── UserAvatar.tsx
│   └── UserProfileCard.tsx
├── model/
│   └── types.ts        # User interface, UserRole enum
├── api/
│   └── fetch-user.ts   # Next.js native fetch wrappers
└── index.ts
```

By keeping entities isolated from features, you ensure that a `UserProfileCard` can be safely imported into the `checkout-flow` feature without creating circular dependencies.

### 4. The `shared/` Layer: Infrastructure

The shared layer contains agnostic code that has no knowledge of the business domain. If a module in `shared/` requires importing something from `entities/` or `features/`, it is an architectural violation.

```text
shared/
├── ui/           # Design system components (Button, Input, Modal)
├── lib/          # Utilities (date formatters, cn/clsx wrappers)
├── api/          # Base API clients (fetch wrappers, Axios instances)
└── config/       # Environment variables, feature flags
```

## Integrating Next.js Specifics

### Handling Server and Client Components
The App Router relies heavily on the `use client` directive. In an FSD architecture, you should push the `use client` directive as far down the component tree as possible, typically into the `ui/` segments of your features or shared UI components.

The public API (`index.ts`) of a feature should explicitly export Server Components and Client Components separately if necessary, though ideally, features are composed by the Server Components in the `app/` layer.

### Data Fetching and Caching
Next.js extends the native `fetch` API for caching and revalidation. These fetch calls should be encapsulated within the `api/` segments of your entities or features. 

```tsx
// entities/product/api/get-product.ts
import { Product } from '../model/types';

export async function getProduct(id: string): Promise<Product> {
  const res = await fetch(`https://api.example.com/products/${id}`, {
    next: { revalidate: 3600, tags: ['product'] }
  });
  return res.json();
}
```
By encapsulating this in the entity layer, any page in the `app/` router can import `getProduct`, and Next.js will automatically deduplicate the requests across the server render.

### Route Handlers vs Server Actions
In the App Router, you have two primary ways to handle mutations and external API access: Route Handlers (`route.ts`) and Server Actions (`'use server'`). 

In our scalable architecture, **Route Handlers** belong in the `app/api/` directory because they represent public-facing HTTP endpoints. However, the *logic* inside the Route Handler should be delegated to a feature or entity service. 

Conversely, **Server Actions** are typically tightly coupled to user interactions (like form submissions). Therefore, Server Actions should live in the `api/` segment of the specific feature they support, as shown in our `auth-form` example earlier. This keeps the mutation logic colocated with the UI that triggers it, significantly improving maintainability.

### Context Providers and Global State
With Server Components, the use of React Context should be minimized and pushed to the leaves of your component tree. When you *do* need global state (e.g., a Theme Provider or a complex client-side store), where does it live?

Providers should be defined in the `app/` layer if they wrap the entire application (e.g., `app/providers.tsx`). However, the actual logic and custom hooks for consuming that context belong in the `shared/` or `entities/` layer. For instance, a theme context would live in `shared/lib/theme`, exported for use across the application, while the `<ThemeProvider>` component is injected at the root layout.

## Strict Rules for Scalability

To maintain this architecture, you must enforce strict cross-import rules, typically using ESLint (`eslint-plugin-boundaries` or similar):

1. **Hierarchy Rule**: A layer can only import from layers below it. `app` -> `features` -> `entities` -> `shared`.
2. **Public API Rule**: Modules must only import from a slice's `index.ts` file. Deep imports (e.g., `import { Button } from '@/shared/ui/button/Button'`) should be restricted in favor of `import { Button } from '@/shared/ui'`.
3. **Colocation Rule**: If a utility or type is used strictly within a single feature or component, colocate it. Do not prematurely promote it to the `shared/` layer.

## Conclusion

Migrating to the Next.js App Router provides a massive leap in performance and capability, but it demands rigorous discipline in project structure. By adopting Feature-Sliced Design principles, you decouple your routing layer from your business logic. 

Your `app/` directory becomes a clean map of your application's routes, while `features/` and `entities/` house the robust, testable, and highly cohesive logic that drives your enterprise frontend. This separation of concerns ensures that as your team and codebase grow, your architecture remains a strong foundation rather than a fragile house of cards.
