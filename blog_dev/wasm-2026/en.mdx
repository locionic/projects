## What Actually Changed: WASI Preview 2 and the Component Model

The two things that made server-side Wasm viable are WASI and the Component Model. They're often mentioned together but solve different problems.

**WASI (WebAssembly System Interface)** gives Wasm modules a way to talk to the host: read files, make network connections, get environment variables. WASI Preview 1 was a flat POSIX-ish namespace. WASI Preview 2 (stable since early 2025) restructured everything into typed capability interfaces defined by **WIT** (WebAssembly Interface Types):

```wit
// http-handler.wit
package my:service;

interface handler {
  use wasi:http/types@0.2.0.{incoming-request, outgoing-response, response-outparam};
  handle: func(request: incoming-request, response-out: response-outparam);
}

world http-service {
  export handler;
}
```

This WIT file is your contract. Tools generate host and guest bindings automatically. The module doesn't know if it's running in Wasmtime, Cloudflare's runtime, or Spin — the host fulfills the interface.

**The Component Model** wraps raw Wasm modules into components that can be linked together. Two components compiled from different languages — say, a Rust image processing library and a Python orchestration layer — can call each other directly via WIT interfaces without going through JSON or HTTP. The runtime wires them together.

## Cloudflare Workers: Real Wasm in Production

Cloudflare Workers runs Wasm natively and is probably the most widely used production Wasm runtime today. Every Worker is a Wasm module executed in an isolate. Cold starts are measured in microseconds, not seconds:

```javascript
// worker.js — loading a compiled Rust Wasm module
import wasm from './my-lib_bg.wasm';
import { init, process_payload } from './my-lib.js';

export default {
  async fetch(request) {
    await init(wasm);
    const body = await request.arrayBuffer();
    const result = process_payload(new Uint8Array(body));
    return new Response(result, {
      headers: { 'content-type': 'application/json' }
    });
  }
};
```

The Rust side compiles to `wasm32-unknown-unknown` with `wasm-bindgen`:

```rust
use wasm_bindgen::prelude::*;
use serde_json::Value;

#[wasm_bindgen]
pub fn process_payload(data: &[u8]) -> String {
    let parsed: Value = serde_json::from_slice(data)
        .unwrap_or(Value::Null);
    // ... processing logic
    serde_json::to_string(&parsed).unwrap()
}
```

Build and deploy:
```bash
wasm-pack build --target bundler
wrangler deploy
```

The module starts in ~0.3ms on cold requests. For comparison, a Node.js Lambda cold start is typically 200-800ms.

## Fermyon Spin: Building HTTP Microservices with Wasm

[Spin](https://developer.fermyon.com/spin) is the clearest example of a Wasm-native backend framework. You write components in Rust, Python, Go, or JS — each component handles a specific route:

```toml
# spin.toml
spin_manifest_version = 2

[application]
name = "api-service"
version = "0.1.0"

[[trigger.http]]
route = "/users/..."
component = "user-handler"

[[trigger.http]]
route = "/auth/..."
component = "auth-handler"

[component.user-handler]
source = "target/wasm32-wasip1/release/user_handler.wasm"
allowed_outbound_hosts = ["https://db.internal"]

[component.auth-handler]
source = "target/wasm32-wasip1/release/auth_handler.wasm"
allowed_outbound_hosts = []
```

The `allowed_outbound_hosts` field is the capability model in action: `auth-handler` has zero network access. Even if someone exploited a bug in your JWT parsing logic, the module can't phone home.

Rust component for the user handler:

```rust
use spin_sdk::http::{IncomingRequest, ResponseBuilder};
use spin_sdk::http_component;
use spin_sdk::variables;

#[http_component]
async fn handle(req: IncomingRequest) -> anyhow::Result<impl IntoResponse> {
    let db_url = variables::get("db_url")?;
    // Spin's built-in SQLite or PostgreSQL via spin_sdk::pg
    let conn = spin_sdk::pg::Connection::open(&db_url).await?;
    let rows = conn.query("SELECT id, name FROM users LIMIT 20", &[]).await?;

    let users: Vec<serde_json::Value> = rows.iter().map(|r| {
        serde_json::json!({
            "id": r.get::<i64>(0),
            "name": r.get::<&str>(1)
        })
    }).collect();

    Ok(ResponseBuilder::new(200)
        .header("content-type", "application/json")
        .body(serde_json::to_vec(&users)?)
        .build())
}
```

Deploy to Fermyon Cloud or self-host with `spin up`. The entire service is a set of `.wasm` files and a TOML — no Dockerfile, no container registry.

## Embedding Wasmtime in a Python Service

If you have an existing Python service and want to run Wasm plugins safely — for example, letting users upload transformation logic you'll execute — Wasmtime's Python bindings are the right tool:

```python
from wasmtime import Store, Module, Linker, WasiConfig
from pathlib import Path

class WasmPluginRunner:
    def __init__(self, wasm_path: str):
        self.store = Store()
        wasi = WasiConfig()
        wasi.inherit_stdout()
        self.store.set_wasi(wasi)

        self.linker = Linker(self.store.engine)
        self.linker.define_wasi()

        module = Module.from_file(self.store.engine, wasm_path)
        self.instance = self.linker.instantiate(self.store, module)

    def run_transform(self, input_data: bytes) -> bytes:
        memory = self.instance.exports(self.store)["memory"]
        transform = self.instance.exports(self.store)["transform"]

        # Allocate in Wasm linear memory, call the function, read result back
        alloc = self.instance.exports(self.store)["alloc"]
        ptr = alloc(self.store, len(input_data))
        memory.write(self.store, input_data, ptr)

        result_ptr = transform(self.store, ptr, len(input_data))
        # Read length prefix + data from result_ptr
        result_len = int.from_bytes(
            memory.read(self.store, result_ptr, result_ptr + 4), 'little'
        )
        return bytes(memory.read(self.store, result_ptr + 4, result_ptr + 4 + result_len))
```

The plugin author compiles their Rust code to `wasm32-wasip2`, ships you the `.wasm` file. They can't read your environment variables, can't open network connections, can't access your filesystem. The sandbox is the security model.

## Performance Reality Check

| Workload | V8 JS | Native | Wasm (Wasmtime) |
|---|---|---|---|
| SHA-256 hash (1MB) | 12ms | 2.1ms | 2.4ms |
| JSON parse (10MB) | 89ms | — | 94ms (using serde) |
| Image resize (Lanczos) | 340ms | 41ms | 48ms |
| Cold start (HTTP handler) | 180ms (Node) | — | 0.3ms |

Wasm is approximately 5-20% slower than native for compute-heavy tasks due to indirect call overhead and bounds checks. For most server workloads that are I/O-bound, this difference doesn't matter. The cold start advantage is the real differentiator in edge/serverless deployments.

## What Wasm Is Still Bad At

Don't use Wasm for:

- **Long-running connections** — WebSockets, SSE. Most Wasm runtimes are designed around request-response patterns.
- **Heavy threading** — The threading model (`wasm-threads`) is supported in browsers but has patchy support in server runtimes.
- **Memory-heavy workloads** — The 4GB linear memory limit isn't a practical issue today, but the single address space means no virtual memory tricks.
- **Rapid iteration** — Compile times for Rust to Wasm are significant. For scripts that change hourly, Python or JS still wins on iteration speed.

## Practical Decision Framework

Use Wasm in production when you need at least two of:
1. **Sub-millisecond cold starts** (edge/serverless)
2. **Plugin isolation** (untrusted user code, multi-tenant)
3. **Polyglot composition** (Rust perf-critical core + Python glue)
4. **Predictable performance** (no GC pauses in the hot path)

Use containers when you need long-lived connections, mature observability tooling, or your team's existing Docker workflow.
