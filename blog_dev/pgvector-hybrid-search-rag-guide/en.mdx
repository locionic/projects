When building a Retrieval-Augmented Generation (RAG) system, retrieval accuracy is everything. If the retrieved documents aren't relevant, your LLM's response won't be either. This is where **pgvector hybrid search** shines. By combining traditional full-text search with vector embeddings, you get the best of both worlds.

In this guide, we'll explore how to build a production-ready RAG architecture using PostgreSQL, the `pgvector` extension, and Reciprocal Rank Fusion (RRF). 

If you are exploring other AI stack components, be sure to check out our overview of [AI Tools](/en/blog/ai-tools).

## The RAG Architecture

Let's look at how a hybrid search RAG architecture operates under the hood. The system performs two parallel searches: a dense vector search for semantic meaning and a sparse keyword search (BM25) for exact matches. Then, it merges the results using Reciprocal Rank Fusion (RRF).

While semantic search is powerful, it sometimes fails when a user searches for specific serial numbers, acronyms, or exact names. Combining it with PostgreSQL full text vector search ensures you catch both exact terms and conceptual matches.

## Setting Up pgvector

Let's walk through how to set up your PostgreSQL vector index for optimal performance. We'll use HNSW (Hierarchical Navigable Small World), which is currently the gold standard for high-performance approximate nearest neighbor (ANN) search.

<Stepper>
  <Step title="Enable Extensions">
    First, you need to install and enable `pgvector` in your database.
    ```sql
    CREATE EXTENSION IF NOT EXISTS vector;
    ```
  </Step>
  <Step title="Create the Table">
    Create a table that stores your documents, their text search vectors (for BM25), and their embeddings.
    ```sql
    CREATE TABLE documents (
        id bigserial PRIMARY KEY,
        content text,
        embedding vector(1536), -- e.g., OpenAI embeddings
        fts tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED
    );
    ```
  </Step>
  <Step title="Create the HNSW Index">
    Create an HNSW index on the embedding column. HNSW provides faster query times and better recall compared to ivfflat.
    ```sql
    CREATE INDEX ON documents 
    USING hnsw (embedding vector_cosine_ops);
    ```
  </Step>
  <Step title="Create the Full-Text Index">
    Add a GIN index to speed up the text search queries.
    ```sql
    CREATE INDEX fts_idx ON documents USING GIN (fts);
    ```
  </Step>
</Stepper>

## Implementing Hybrid Search with RRF

To actually perform the hybrid search, you'll query both indexes and merge them. Typically, this is done via a common table expression (CTE) using Reciprocal Rank Fusion (RRF). 

Here is a simplified example of how you might structure the query:

```sql
WITH vector_search AS (
  SELECT id, content, 
         RANK() OVER (ORDER BY embedding <=> '[0.1, 0.2, ...]') AS rank
  FROM documents
  ORDER BY embedding <=> '[0.1, 0.2, ...]'
  LIMIT 50
),
keyword_search AS (
  SELECT id, content,
         RANK() OVER (ORDER BY ts_rank_cd(fts, plainto_tsquery('english', 'search terms')) DESC) AS rank
  FROM documents
  WHERE fts @@ plainto_tsquery('english', 'search terms')
  ORDER BY ts_rank_cd(fts, plainto_tsquery('english', 'search terms')) DESC
  LIMIT 50
)
SELECT 
  COALESCE(v.id, k.id) as id,
  COALESCE(v.content, k.content) as content,
  (COALESCE(1.0 / (60 + v.rank), 0.0) + COALESCE(1.0 / (60 + k.rank), 0.0)) as rrf_score
FROM vector_search v
FULL OUTER JOIN keyword_search k ON v.id = k.id
ORDER BY rrf_score DESC
LIMIT 10;
```

This ensures that documents ranking high in both semantic and keyword search are boosted to the top!
