## Introduction

As AI-driven applications continue to mature, the need for efficient vector search is paramount. While dedicated vector databases have their place, the ability to store and query embeddings directly alongside relational data simplifies architecture dramatically. Enter `pgvector`, an open-source extension for PostgreSQL that enables production-ready vector search.

In this post, we'll explore how to build scalable vector search in PostgreSQL using `pgvector`, covering setup, indexing strategies, and performance optimization for production workloads.

## Why pgvector?

Using PostgreSQL with `pgvector` offers several compelling advantages:
- **Unified Data Store:** No need to synchronize data between your primary relational database and a separate vector database.
- **ACID Compliance:** You get the reliability and consistency guarantees of PostgreSQL.
- **Familiar Tooling:** Leverage existing SQL knowledge, ORMs, and database management tools.

## Setting Up pgvector

First, ensure the extension is installed in your PostgreSQL instance. 

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

Next, create a table with a `vector` column. The dimension size must match the output of your embedding model (e.g., 1536 for OpenAI's `text-embedding-3-small`).

```sql
CREATE TABLE documents (
    id bigserial PRIMARY KEY,
    content text NOT NULL,
    embedding vector(1536)
);
```

## Inserting Data

Inserting vectors is straightforward. Most client libraries support array syntax that maps directly to the `vector` type.

```sql
INSERT INTO documents (content, embedding) 
VALUES ('The quick brown fox', '[0.1, 0.2, 0.3, ...]');
```

## Performing Vector Searches

`pgvector` supports several distance metrics:
- `<->` L2 distance (Euclidean)
- `<#>` Negative inner product
- `<=>` Cosine distance

For cosine similarity (commonly used for text embeddings), you can query like this:

```sql
SELECT id, content, 1 - (embedding <=> '[0.1, 0.2, ...]') AS similarity
FROM documents
ORDER BY embedding <=> '[0.1, 0.2, ...]'
LIMIT 5;
```

## Indexing for Production Scale

Exact nearest neighbor search (k-NN) requires scanning every row, which does not scale for millions of vectors. `pgvector` provides two index types for approximate nearest neighbor (ANN) search: HNSW (Hierarchical Navigable Small World) and IVFFlat.

### HNSW Indexing

HNSW is generally the preferred index for production workloads in 2026. It offers better query performance and recall than IVFFlat and doesn't require a training step.

```sql
CREATE INDEX ON documents USING hnsw (embedding vector_cosine_ops);
```

**Tuning HNSW:**
- `m`: The maximum number of connections per layer (default 16).
- `ef_construction`: The size of the dynamic list for the nearest neighbors (default 64). Higher values increase build time but improve recall.

### IVFFlat Indexing

If you have memory constraints, IVFFlat might still be appropriate, but it requires data to be present in the table before creating the index.

## Best Practices

1. **Warm Up the Cache:** Vector operations are memory-intensive. Ensure your server has sufficient RAM to hold the index in memory.
2. **Batch Operations:** When generating and inserting embeddings, process them in batches to reduce network overhead and transaction costs.
3. **Hybrid Search:** Combine vector similarity with traditional full-text search or metadata filtering for highly accurate retrieval augmented generation (RAG) pipelines.

```sql
-- Example Hybrid Search
SELECT content
FROM documents
WHERE category = 'tech'
ORDER BY embedding <=> '[...]'
LIMIT 10;
```

## Conclusion

`pgvector` transforms PostgreSQL into a highly capable vector database, perfectly suited for the majority of AI applications. By understanding indexing strategies and distance metrics, you can build production-ready vector search that is both fast and reliable.
