## eBPF Là Gì? Máy Ảo Nhúng Cấp Kernel

eBPF (extended Berkeley Packet Filter) là một công nghệ mang tính cách mạng cho phép chúng ta chạy các chương trình sandboxed ngay bên trong nhân Linux mà không cần sửa đổi mã nguồn kernel hay nạp các kernel module rủi ro. Hãy hình dung nó như một máy ảo nhỏ gọn, siêu hiệu quả, hoạt động theo cơ chế hướng sự kiện (event-driven) được nhúng sâu vào lòng kernel. Khi các sự kiện cụ thể xảy ra (ví dụ: một system call được gọi, một gói tin mạng được nhận, một hàm kernel được kích hoạt), kernel sẽ thực thi chương trình eBPF đã được nạp sẵn để thu thập số liệu, biến đổi hành vi hoặc thực thi chính sách bảo mật.

Kiến trúc này được xây dựng trên bốn thành phần cốt lõi:

1.  **eBPF Programs (Chương trình eBPF):** Đây là các đoạn mã ngắn được viết bằng một tập con bị giới hạn của ngôn ngữ C. Chúng được biên dịch thành bytecode eBPF thông qua compiler như Clang/LLVM.
2.  **Hooks (Điểm Gắn):** Đây là các điểm được định nghĩa rõ ràng trong luồng mã của kernel nơi chương trình eBPF có thể được đính kèm. Các loại hook chính bao gồm **kprobes** (can thiệp động vào hàm kernel), **tracepoints** (các điểm trace ổn định do kernel cung cấp), **XDP** (eXpress Data Path chuyên xử lý mạng tốc độ cực cao) và **TC** (Traffic Control hooks).
3.  **eBPF Maps:** Tập hợp các cấu trúc dữ liệu key-value nằm trong bộ nhớ kernel. Maps là cơ chế chính để các chương trình eBPF lưu trữ trạng thái và truyền dữ liệu lên các ứng dụng userspace (cũng như giữa các chương trình eBPF với nhau). Có nhiều loại map như hash map, mảng và ring buffer hiệu năng cao.
4.  **The Verifier (Trình Kiểm Duyệt):** Trọng tâm an ninh tuyệt đối của eBPF. Trước khi bất kỳ bytecode eBPF nào được nạp vào kernel, verifier sẽ thực hiện phân tích tĩnh để chứng minh chương trình an toàn 100%. Nó đảm bảo rằng chương trình luôn kết thúc (cấm vòng lặp vô tận), không truy cập bộ nhớ ngoài biên và không bao giờ có thể gây kernel panic. Nếu chương trình vi phạm dù chỉ một quy tắc nhỏ, nó sẽ bị từ chối ngay lập tức.

Sau khi vượt qua vòng kiểm duyệt, bytecode eBPF sẽ được trình biên dịch Just-In-Time (JIT) dịch thành mã máy gốc của kiến trúc CPU máy chủ, mang lại hiệu năng thực thi gần như tức thời.

### Quy Trình Phát Triển và Thực Thi eBPF

## Thực Hành: Đo Độ Trễ System Call `openat` Trong Thực Tế

Hãy cùng xây dựng một công cụ thực tế để thấy rõ sức mạnh của eBPF. Mục tiêu của chúng ta là đo lường độ trễ của system call `openat` — một trong những nguồn gây nghẽn I/O wait phổ biến nhất. Chúng ta sẽ ghi lại PID, tên tiến trình (comm), đường dẫn tệp tin và độ trễ (latency tính bằng nanosecond) cho mỗi lần gọi.

Chúng ta thực hiện điều này bằng cách gắn các chương trình eBPF vào hai tracepoints: `sys_enter_openat` và `sys_exit_openat`.

### Chương Trình Kernel eBPF (C)

Chương trình C chứa toàn bộ logic chạy bên trong nhân. Chúng ta sử dụng `BPF_MAP_TYPE_HASH` để lưu mốc thời gian bắt đầu khi tiến trình bước vào syscall và `BPF_MAP_TYPE_RINGBUF` để gửi sự kiện hoàn chỉnh lên userspace. Ring buffer là giải pháp hiện đại, tối ưu bộ nhớ và không bao giờ đánh rơi dữ liệu khi hệ thống bị quá tải.

```c
// File: syscall_tracer.c
#include "vmlinux.h"
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>
#include <bpf/bpf_core_read.h>

#define MAX_FILENAME_LEN 256

// Cấu trúc sự kiện chuyển lên userspace
struct event {
    u32 pid;
    u64 latency_ns;
    char comm[16];
    char filename[MAX_FILENAME_LEN];
};

// Map lưu thời điểm bắt đầu theo Thread ID (TID)
struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 10240);
    __type(key, u32);
    __type(value, u64);
} start SEC(".maps");

// Ring buffer truyền sự kiện lên userspace
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024); // 256 KB
} events SEC(".maps");

// Gắn vào tracepoint lúc vào system call openat
SEC("tracepoint/syscalls/sys_enter_openat")
int tracepoint__syscalls__sys_enter_openat(struct trace_event_raw_sys_enter* ctx) {
    u64 id = bpf_get_current_pid_tgid();
    u32 tid = (u32)id;
    u64 ts = bpf_ktime_get_ns();

    // Lưu timestamp bắt đầu
    bpf_map_update_elem(&start, &tid, &ts, BPF_ANY);
    return 0;
}

// Gắn vào tracepoint lúc thoát system call openat
SEC("tracepoint/syscalls/sys_exit_openat")
int tracepoint__syscalls__sys_exit_openat(struct trace_event_raw_sys_exit* ctx) {
    u64 id = bpf_get_current_pid_tgid();
    u32 tid = (u32)id;
    u64 *ts_ptr;

    // Tìm kiếm timestamp bắt đầu
    ts_ptr = bpf_map_lookup_elem(&start, &tid);
    if (ts_ptr == 0) {
        return 0; // Bỏ qua nếu lỡ sự kiện enter
    }

    u64 latency = bpf_ktime_get_ns() - *ts_ptr;
    bpf_map_delete_elem(&start, &tid);

    // Lọc bỏ những sự kiện quá nhanh (< 1 microsecond)
    if (latency < 1000) {
        return 0;
    }

    // Đặt chỗ trên ring buffer
    struct event *e = bpf_ringbuf_reserve(&events, sizeof(*e), 0);
    if (!e) {
        return 0;
    }

    // Điền dữ liệu sự kiện
    u32 pid = id >> 32;
    e->pid = pid;
    e->latency_ns = latency;

    // Lấy tên lệnh tiến trình
    bpf_get_current_comm(&e->comm, sizeof(e->comm));

    // Lấy đường dẫn tệp từ tham số context (ctx->args[1])
    // Sử dụng bpf_probe_read_user_str để đọc an toàn bộ nhớ userspace
    const char __user *filename_ptr = (const char __user *)ctx->args[1];
    bpf_probe_read_user_str(&e->filename, sizeof(e->filename), filename_ptr);

    // Đẩy sự kiện lên userspace
    bpf_ringbuf_submit(e, 0);
    return 0;
}

char LICENSE[] SEC("license") = "GPL";
```

### Userspace Loader 1: Python Kết Hợp BCC

BPF Compiler Collection (BCC) là bộ công cụ xuất sắc để viết eBPF, đặc biệt phù hợp cho các script phân tích nhanh và thử nghiệm logic. BCC tích hợp sẵn Clang/LLVM và sử dụng frontend Python (hoặc Lua) để điều phối toàn bộ quy trình ngay lúc chạy.

Dưới đây là cách nạp và tương tác với chương trình C bằng Python BCC:

```python
#!/usr/bin/python3
# File: bcc_loader.py
from bcc import BPF
import ctypes as ct

# Mã nguồn C từ syscall_tracer.c được nhúng trực tiếp
bpf_text = """
#include <uapi/linux/ptrace.h>
#include <linux/fs.h>
#include <linux/sched.h>

#define MAX_FILENAME_LEN 256

struct event {
    u32 pid;
    u64 latency_ns;
    char comm[TASK_COMM_LEN];
    char filename[MAX_FILENAME_LEN];
};
BPF_RINGBUF_OUTPUT(events, 8);

BPF_HASH(start, u32);

int tracepoint__syscalls__sys_enter_openat(struct tracepoint__syscalls__sys_enter_openat *args) {
    u64 id = bpf_get_current_pid_tgid();
    u32 tid = (u32)id;
    u64 ts = bpf_ktime_get_ns();
    start.update(&tid, &ts);
    return 0;
}

int tracepoint__syscalls__sys_exit_openat(struct tracepoint__syscalls__sys_exit_openat *args) {
    u64 id = bpf_get_current_pid_tgid();
    u32 tid = (u32)id;
    u64 *ts_ptr = start.lookup(&tid);

    if (ts_ptr == 0) {
        return 0;
    }

    u64 latency = bpf_ktime_get_ns() - *ts_ptr;
    start.delete(&tid);

    if (latency < 1000) {
        return 0;
    }

    struct event *e = events.ringbuf_reserve(sizeof(struct event));
    if (!e) {
        return 0;
    }

    e->pid = id >> 32;
    e->latency_ns = latency;
    bpf_get_current_comm(&e->comm, sizeof(e->comm));
    
    const char __user* filename_ptr = (const char __user*)args->filename;
    bpf_probe_read_user_str(&e->filename, sizeof(e->filename), filename_ptr);

    events.ringbuf_submit(e, 0);
    return 0;
}
"""

class Event(ct.Structure):
    _fields_ = [
        ("pid", ct.c_uint),
        ("latency_ns", ct.c_ulonglong),
        ("comm", ct.c_char * 16),
        ("filename", ct.c_char * 256),
    ]

def print_event(cpu, data, size):
    event = ct.cast(data, ct.POINTER(Event)).contents
    print(f"{event.pid:<10} {event.comm.decode():<16} {event.latency_ns / 1000:<10.2f} us   '{event.filename.decode()}'")

b = BPF(text=bpf_text)
b["events"].open_ring_buffer(print_event)

print(f"{'PID':<10} {'COMM':<16} {'LATENCY':<13} {'FILENAME'}")

while True:
    try:
        b.ring_buffer_poll()
    except KeyboardInterrupt:
        exit()
```

Sức mạnh của BCC nằm ở việc biên dịch runtime. Nó giúp thử nghiệm cực nhanh nhưng đòi hỏi phải cài đặt Clang/LLVM trên máy chủ đích và có độ trễ khởi động. Đối với môi trường production khắt khe, giải pháp biên dịch tĩnh (ahead-of-time) vượt trội hơn hẳn.

### Userspace Loader 2: Go với thư viện cilium/ebpf

Đối với các dịch vụ production, Golang kết hợp cùng thư viện `cilium/ebpf` là tiêu chuẩn vàng: hiệu năng đỉnh cao, tự chứa (self-contained) và không phụ thuộc runtime. Mô hình này áp dụng kiến trúc "Biên dịch một lần, chạy mọi nơi" (Compile Once, Run Everywhere - CO-RE).

Trước tiên, cài đặt công cụ `bpf2go`:

```bash
# Cài đặt bpf2go
go install github.com/cilium/ebpf/cmd/bpf2go@latest
```

Chạy lệnh `go generate` để biên dịch `syscall_tracer.c` thành tệp đối tượng ELF và tự động sinh mã nguồn Go struct:

```go
// File: go_loader.go
package main

import (
    "bytes"
    "encoding/binary"
    "errors"
    "log"
    "os"
    "os/signal"
    "syscall"

    "github.com/cilium/ebpf/link"
    "github.com/cilium/ebpf/ringbuf"
)

//go:generate go run github.com/cilium/ebpf/cmd/bpf2go syscall_bpf syscall_tracer.c -- -O2 -g -Wall

func main() {
    stopper := make(chan os.Signal, 1)
    signal.Notify(stopper, os.Interrupt, syscall.SIGTERM)

    objs := syscall_bpfObjects{}
    if err := loadSyscall_bpfObjects(&objs, nil); err != nil {
        log.Fatalf("loading objects: %v", err)
    }
    defer objs.Close()

    enter_tp, err := link.Tracepoint("syscalls", "sys_enter_openat", objs.TracepointSyscallsSysEnterOpenat, nil)
    if err != nil {
        log.Fatalf("attaching enter tracepoint: %v", err)
    }
    defer enter_tp.Close()

    exit_tp, err := link.Tracepoint("syscalls", "sys_exit_openat", objs.TracepointSyscallsSysExitOpenat, nil)
    if err != nil {
        log.Fatalf("attaching exit tracepoint: %v", err)
    }
    defer exit_tp.Close()

    rd, err := ringbuf.NewReader(objs.Events)
    if err != nil {
        log.Fatalf("opening ringbuf reader: %v", err)
    }
    defer rd.Close()

    go func() {
        <-stopper
        rd.Close()
    }()

    log.Println("Đang lắng nghe sự kiện openat..")
    log.Printf("%-10s %-16s %-13s %s\n", "PID", "COMM", "LATENCY (us)", "FILENAME")

    var event syscall_bpfEvent
    for {
        record, err := rd.Read()
        if err != nil {
            if errors.Is(err, ringbuf.ErrClosed) {
                log.Println("Đã nhận tín hiệu dừng, thoát..")
                return
            }
            log.Printf("lỗi đọc ringbuf: %v", err)
            continue
        }

        if err := binary.Read(bytes.NewBuffer(record.RawSample), binary.LittleEndian, &event); err != nil {
            log.Printf("lỗi parse event: %v", err)
            continue
        }
        
        comm := string(event.Comm[:bytes.IndexByte(event.Comm[:], 0)])
        filename := string(event.Filename[:bytes.IndexByte(event.Filename[:], 0)])

        log.Printf("%-10d %-16s %-13.2f %s\n", event.Pid, comm, float64(event.LatencyNs)/1000.0, filename)
    }
}
```

Giải pháp Go đóng gói toàn bộ chương trình eBPF vào một binary tĩnh duy nhất, không cần cài đặt compiler hay header kernel trên node production, cực kỳ lý tưởng cho Kubernetes container.

## So Sánh eBPF vs. Sidecar: Nghiên Cứu Điển Hình Từ Cilium

Sự tốn kém của "thuế quan sát" thể hiện rõ ràng nhất trong kiến trúc Service Mesh. Một mesh truyền thống như Istio sẽ chèn một sidecar proxy (Envoy) vào từng application pod. Proxy này can thiệp vào mọi luồng giao tiếp để cung cấp định tuyến L7, mTLS và đo lường metrics.

Cái giá phải trả vô cùng đắt đỏ:
1.  **Độ trễ (Latency):** Mọi request phải đi qua TCP/IP stack hai lần: từ ứng dụng sang sidecar, rồi từ sidecar ra ngoài mạng.
2.  **Tiêu hao tài nguyên:** Mỗi sidecar là một process riêng biệt tiêu tốn CPU và RAM, có thể làm tăng gấp đôi chi phí hạ tầng của cluster.
3.  **Độ phức tạp:** Thêm hàng trăm nghìn container cần bảo trì, vá lỗi bảo mật và khởi động lại khi có cập nhật.

Cilium — giải pháp CNI và Service Mesh xây dựng hoàn toàn trên eBPF — loại bỏ hoàn toàn mô hình sidecar:

*   **Tại Tầng Socket:** Chương trình eBPF đính kèm vào socket hooks (`cgroup/sock_addr`) có thể kiểm tra và chuyển hướng traffic ngay lập tức. Đối với các chính sách L7 (HTTP/gRPC), Cilium chuyển tiếp trực tiếp sang một Envoy proxy duy nhất trên mỗi Node thay vì trên từng Pod.
*   **Tại Tầng Gói Tin (Packet Layer):** Đối với load balancing L3/L4 và network policy, eBPF hoạt động trên hook **TC** và **XDP**, xử lý trực tiếp gói tin trong kernel với thông lượng vượt trội so với `iptables` hay `IPVS`.
*   **Quan Sát Trong Suốt (Transparent Observability):** Vì eBPF nhìn thấy toàn bộ sự kiện mạng ở tầng kernel, Cilium tự động tạo ra các metrics phong phú (HTTP status, độ trễ, DNS lookup, TCP drop) cho 100% ứng dụng mà không cần sửa một dòng code hay cắm bất kỳ sidecar nào.

<FAQ title="Các Câu Hỏi Thường Gặp Về eBPF">
  <Question>Cơ chế hoạt động của eBPF Verifier là gì và giới hạn của nó ra sao?</Question>
  <Answer>
    Verifier là một công cụ phân tích tĩnh coi chương trình eBPF như một đồ thị có hướng không chu trình (DAG). Nhiệm vụ của nó là chứng minh tính an toàn trước khi chạy:
    - **Không có vòng lặp vô tận:** Cấm nhảy lùi (backward jump) không giới hạn.
    - **An toàn bộ nhớ:** Kiểm tra con trỏ không bao giờ trỏ tới vùng cấm, bắt buộc kiểm tra NULL trước khi dereference.
    - **Kích thước stack:** Giới hạn stack tối đa 512 byte.
    
    Giới hạn chính là độ phức tạp: Nếu một chương trình vượt quá giới hạn ~1 triệu chỉ lệnh cần phân tích, verifier sẽ từ chối nạp. Kỹ sư phải chia nhỏ logic phức tạp thành các tail call liên kết với nhau.
  </Answer>
  <Question>Sự khác biệt giữa kprobes, tracepoints và uprobes là gì?</Question>
  <Answer>
    Đây là các điểm gắn (attachment points) với mức độ ổn định khác nhau:
    - **Tracepoints:** Các hook ổn định, được định nghĩa rõ trong mã nguồn Linux kernel. Chúng cung cấp API ổn định qua các phiên bản kernel, là lựa chọn số 1 cho production.
    - **kprobes:** Các probe động gắn vào điểm vào/ra của hầu như bất kỳ hàm kernel nào. Rất mạnh để debug chuyên sâu nhưng dễ bị gãy khi nâng cấp phiên bản kernel do hàm bị đổi tên hoặc inline.
    - **uprobes:** Gắn eBPF vào các hàm trong ứng dụng userspace hoặc thư viện dùng chung (như libc, OpenSSL) để trace ứng dụng mà không cần compile lại mã nguồn.
  </Answer>
  <Question>Nên chọn BCC hay libbpf/cilium-ebpf cho môi trường Production?</Question>
  <Answer>
    - **BCC:** Thích hợp cho việc nghiên cứu, thử nghiệm, viết tool ad-hoc cục bộ vì nó biên dịch C bằng Clang/LLVM ngay lúc chạy.
    - **libbpf-based (cilium/ebpf trong Go, libbpf-rs trong Rust):** Lựa chọn chuẩn cho production. Tuân thủ chuẩn CO-RE, biên dịch sẵn sang ELF binary, tương thích đa phiên bản kernel nhờ BTF (BPF Type Format) và không đòi hỏi trình biên dịch trên host.
  </Answer>
</FAQ>

## Kết Luận: Tương Lai Thuộc Về Khả Năng Lập Trình Kernel

eBPF đại diện cho một bước nhảy vọt mang tính nền tảng trong kiến trúc hệ điều hành hiện đại. Nó đưa chúng ta thoát khỏi kỷ nguyên của các kernel API cứng nhắc và các userspace agent nặng nề, tiến vào thời đại mà chúng ta có thể lập trình trực tiếp nhân hệ điều hành một cách an toàn và thần tốc.

Đối với observability, chúng ta cuối cùng đã có thể xóa bỏ hoàn toàn "thuế quan sát". Chúng ta thu thập dữ liệu sâu sắc nhất về system call, cấp phát bộ nhớ và luồng mạng ngay từ nguồn chân lý đích thực — kernel Linux — với chi phí tối thiểu.

**Hành Động Khuyến Nghị Cho Kỹ Sư Hệ Thống:**
1.  **Bắt đầu với BCC:** Thử nghiệm trên máy dev với kho công cụ phong phú của BCC để làm quen với khả năng của eBPF.
2.  **Profile Ứng Dụng Thực Tế:** Dùng eBPF để phát hiện các điểm nghẽn I/O wait, latency của database connection và memory allocation.
3.  **Đầu Tư Vào CO-RE Khi Lên Prod:** Xây dựng agent giám sát bằng Go (`cilium/ebpf`) hoặc Rust (`libbpf-rs`) để có binary tĩnh gọn nhẹ.
4.  **Đánh Giá Lại Service Mesh:** Nghiên cứu áp dụng Cilium để tinh giản hạ tầng mạng Kubernetes và loại bỏ sidecar proxy.
