## The Illusion of Type Safety

TypeScript is often described as the savior of modern JavaScript applications. It catches typos, autocompletes object properties, and prevents calling undefined functions during development.

Yet, hundreds of production Next.js and Node.js applications crash every day with:
`TypeError: Cannot read properties of undefined (reading 'map')` or `TypeError: data.slice is not a function`.

Why does this happen despite having strict TypeScript compiler settings enabled?

Because **TypeScript does not exist at runtime**. When your code compiles, every interface, type alias, generic parameter, and type assertion (`as User`) is erased from the JavaScript bundle. At the network boundary—incoming HTTP requests, Next.js Server Action payloads, third-party webhook events, and database query results—the data running through your code is completely untyped.

To achieve true end-to-end reliability, you must validate data when it enters your system. That is where **Zod** becomes essential.

## Refactoring Vulnerable Server Actions to Zod

Look at a common vulnerability in Next.js Server Actions where developers use type assertions without runtime validation:

  language="typescript"
  beforeCode={`// ❌ Vulnerable: Blind type assertion in Next.js Server Action
'use server';

interface CreateUserInput {
  email: string;
  age: number;
  role: 'admin' | 'user';

export async function createUser(formData: FormData) {
  // Danger! 'as any' or manual object creation has zero guarantees.
  // If a malicious client sends email: 12345 or age: "twenty", this crashes or corrupts the DB!
  const rawData = Object.fromEntries(formData);
  const data = rawData as unknown as CreateUserInput;

  await db.user.create({
    data: {
      email: data.email.toLowerCase(), // CRASH if email is undefined or a number!
      age: data.age,
      role: data.role,
    }
  });
}`}
  afterCode={`// ✅ Secure: Strict runtime validation with auto-inferred types
'use server';

import { z } from 'zod';

export const CreateUserSchema = z.object({
  email: z.string().email('Invalid email address').toLowerCase(),
  age: z.coerce.number().int().min(18, 'Must be at least 18 years old'),
  role: z.enum(['admin', 'user']).default('user'),
});

// Infer the TypeScript type directly from the schema — never duplicate types!
export type CreateUserInput = z.infer<typeof CreateUserSchema>;

export async function createUser(formData: FormData) {
  const result = CreateUserSchema.safeParse(Object.fromEntries(formData));

  if (!result.success) {
    // Return structured field errors without throwing unhandled server exceptions
    return { success: false, errors: result.error.flatten().fieldErrors };
  }

  // result.data is strictly typed and guaranteed safe
  const { email, age, role } = result.data;
  await db.user.create({ data: { email, age, role } });

  return { success: true };
}`}

## 4 Power Techniques for Advanced Zod Usage

### 1. `z.coerce` for Form Data and URL Search Params
When parsing HTML `FormData` or Next.js `searchParams`, everything arrives as strings (`"42"`, `"true"`). Instead of writing manual `parseInt()` or `Boolean()` calls:
```typescript
const FilterSchema = z.object({
  page: z.coerce.number().default(1),
  limit: z.coerce.number().default(20),
  active: z.coerce.boolean().default(true),
});
```

### 2. `safeParse` vs `parse`
- `schema.parse(data)` throws a `ZodError` if validation fails. Use this only inside try/catch blocks or top-level API handlers with global error middleware.
- `schema.safeParse(data)` never throws. It returns a discriminated union: `{ success: true, data }` or `{ success: false, error }`. This is ideal for Next.js Server Actions and React Hook Form.

### 3. Schema Composition and Inheritance
Zod schemas are composable. You can extend, merge, and pick fields:
```typescript
const BaseUserSchema = z.object({
  id: z.string().uuid(),
  createdAt: z.date(),
});

const UpdateProfileSchema = BaseUserSchema.extend({
  bio: z.string().max(500).optional(),
  displayName: z.string().min(2),
});
```

### 4. Custom Refinements with `.refine()`
For cross-field validation (such as ensuring a "confirm password" matches "password"):
```typescript
const PasswordChangeSchema = z.object({
  newPassword: z.string().min(8),
  confirmPassword: z.string().min(8),
}).refine((data) => data.newPassword === data.confirmPassword, {
  message: "Passwords do not match",
  path: ["confirmPassword"],
});
```
