If you're building with Next.js (or any SSR React framework), you will run into hydration errors. Let's break down exactly what they mean, why they happen, and the three most common ways to fix them.

## What Actually Is "Hydration"?

Before we fix the error, we need to understand the process. Next.js does two things when a user requests a page:

1. **Pre-rendering (Server Side):** Next.js runs your React components on the server, generates raw HTML, and sends it to the browser. The user sees the page instantly, but it isn't interactive yet (buttons don't work, inputs are inert).
2. **Hydration (Client Side):** React runs on the client, downloads the JavaScript bundle, walks the server-rendered HTML structure, and attaches event listeners (like `onClick`) to make it alive.

Here is the golden rule of SSR: **The HTML generated on the server must exactly match the HTML generated on the client's first render.**

If there is even a single character of difference, React panics. It throws a hydration mismatch error, discards the server HTML, and rebuilds the page from scratch. This slows down your site and ruins the performance benefits of SSR.

## Villain #1: Client-Only Globals (`window` and `localStorage`)

The most common mistake is referencing browser APIs directly in your render path. The server has no concept of `window` or `document`.

```tsx
// ❌ THIS WILL CRASH ON THE SERVER
function MyComponent() {
  const width = window.innerWidth; // window is undefined on the server!
  return <div>Width: {width}</div>;
}
```

Even if you wrap it in a typeof check to prevent the crash, you still get a hydration error because the server output will be different from the client output.

<DiffView
  oldCode={`// ❌ Hydration Error: server gets "Server", client gets width
function ResponsiveLayout() {
  const isMobile = typeof window !== 'undefined' && window.innerWidth < 768;
  return <div>{isMobile ? 'Mobile' : 'Desktop'}</div>;
}`}
  newCode={`// ✅ Safe: state is initialized on client mount
import { useState, useEffect } from 'react';

function ResponsiveLayout() {
  const [isMobile, setIsMobile] = useState(false);

  useEffect(() => {
    setIsMobile(window.innerWidth < 768);
  }, []);

  return <div>{isMobile ? 'Mobile' : 'Desktop'}</div>;
}`}
  language="tsx"
  mode="unified"
/>

<Callout type="info" title="The Hook Strategy">
  For browser APIs, always defer the state update to `useEffect`. Since `useEffect` only runs in the browser after mount, it never executes on the server. The initial HTML matches, and the client updates the UI safely afterward.
</Callout>

## Villain #2: Dynamic Data (Dates, Times, and Random Numbers)

If you display the current time or a random number, the server will generate one value, and the client (running milliseconds later) will generate a different one.

```tsx
// ❌ Server: "Rendered at 10:00:00", Client: "Rendered at 10:00:02"
function CurrentTime() {
  return <div>Time: {new Date().toLocaleTimeString()}</div>;
}
```

There are two ways to solve this depending on what you need.

### Solution A: Defer to Client Mount (Recommended)

If the data doesn't need to be there for SEO, wait until the component mounts to show it.

<Stepper>
  <Step title="Initialize Mount State">
    Create a boolean state to track if the component has mounted in the browser.
  </Step>
  <Step title="Trigger in useEffect">
    Flip the boolean to `true` inside `useEffect`.
  </Step>
  <Step title="Conditional Render">
    Show a loading placeholder on the server and the actual date on the client.
  </Step>
</Stepper>

```tsx
import { useState, useEffect } from 'react';

export default function CurrentTime() {
  const [mounted, setMounted] = useState(false);

  useEffect(() => {
    setMounted(true);
  }, []);

  if (!mounted) return <div>Loading time...</div>;

  return <div>Time: {new Date().toLocaleTimeString()}</div>;
}
```

### Solution B: Suppress Warning (For Static Content)

If the discrepancy is harmless (like a static timezone rendering or an intentional mismatch), you can tell React to ignore it using the `suppressHydrationWarning` attribute.

```tsx
// This disables the console error for this specific element
<div suppressHydrationWarning>Time: {new Date().toLocaleTimeString()}</div>
```

<Callout type="warning" title="Warning">
  `suppressHydrationWarning` only works one level deep and does not fix the underlying performance cost of React mismatch rebuilding. Use it sparingly for simple text nodes (like dates or timestamps), not large UI trees.
</Callout>

## Villain #3: Invalid HTML Tag Nesting

This is the sneakiest cause of hydration errors. It has nothing to do with JavaScript state, but rather the way browsers parse invalid HTML tags.

If you nest a `<div>` inside a `<p>` tag, the browser's HTML parser will automatically close the `<p>` tag before the `<div>` is opened. This transforms your intended DOM structure into something completely different.

React expects the structure on the server to match the DOM structure parsed by the browser. When the browser rewrites the tags, React spots the mismatch and errors out.

Common HTML nesting mistakes that trigger hydration errors:
* Placing `<div>` or `<p>` inside another `<p>`
* Placing `<ul>` or `<ol>` directly inside a `<p>`
* Putting a `<tr>` directly under a `<table>` instead of wrapping it in `<tbody>`
* Putting block elements (`h1`, `form`, `section`) inside inline elements (`a`, `span`)

## How to Debug Hydration Errors: Step-by-Step

Next.js 14+ gives you much better error overlays than before — but the trace can still be cryptic. Here is the exact workflow I use every time:

### Step 1 — Read the error diff in the overlay

When a hydration error fires in development, Next.js shows a red overlay with the **server output** and **client output** side by side. The first thing to do is read both sides carefully:

```
Server rendered:
  <div class="theme-dark">

Client rendered:
  <div class="theme-light">
```

This immediately tells you the mismatch is theme-related — look for `localStorage` or `cookies` being read during render.

### Step 2 — Test in Incognito with extensions disabled

Browser extensions are a silent hydration killer. Ad blockers, grammar checkers, and translator extensions inject DOM nodes or modify attributes *before* React hydrates. The server never saw those changes, so React panics.

**Always reproduce the error in an Incognito window** before you do anything else. If the error disappears in Incognito, a browser extension is your culprit — not your code.

### Step 3 — Enable Next.js Turbopack for better diffs

```bash
next dev --turbopack
```

Turbopack gives more precise hydration error messages than the default Webpack mode, including the exact component path and a character-level diff of the mismatch.

### Step 4 — Bisect with `suppressHydrationWarning` temporarily

If you can't find the source, add `suppressHydrationWarning` to your root `<body>` temporarily. This silences all hydration errors. Then remove it from one child component at a time until the error reappears — that's your culprit component.

```tsx
// Temporary! Remove after finding the bug.
<body suppressHydrationWarning>
```

<Callout type="warning" title="Remove After Debugging">
  `suppressHydrationWarning` on `<body>` silences *all* hydration warnings globally. It's a debugging tool only — never ship it to production as a permanent fix.
</Callout>

### Step 5 — Search for the common patterns with grep

Run these in your project root to find the most likely offenders:

```bash
# Find direct localStorage / sessionStorage reads in render paths
grep -rn "localStorage\|sessionStorage" src/ --include="*.tsx" --include="*.ts" | grep -v "useEffect"

# Find components using window without a guard
grep -rn "window\." src/ --include="*.tsx" | grep -v "typeof window"

# Find suppressHydrationWarning usage (should be rare)
grep -rn "suppressHydrationWarning" src/ --include="*.tsx"

# Find dynamic imports without ssr:false on heavy chart/map components
grep -rn "import dynamic" src/ --include="*.tsx"
```

Each result from the first two greps is a potential hydration error waiting to happen.

## Villain #4: Third-Party Libraries That Mutate the DOM

This is the hardest category to debug because the bug isn't in *your* code at all. Libraries like jQuery plugins, legacy analytics scripts, or embedded widgets sometimes manipulate the DOM directly — adding attributes, wrapping nodes, or injecting elements.

React's hydration expects the DOM to be exactly what the server produced. Any external DOM mutation before hydration completes will cause a mismatch.

**Common offenders:**
- **Google Translate widget** — rewrites all text nodes in the DOM
- **Hotjar / FullStory** — inject iframe or attribute overlays
- **Legacy jQuery plugins** — call `.addClass()` or `.wrap()` on mount
- **Browser translate feature** — same as Google Translate widget

**The fix:** Load these scripts *after* hydration using `next/script` with `strategy="afterInteractive"`:

```tsx
import Script from 'next/script'

export default function Layout({ children }) {
  return (
    <>
      {children}
      {/* Load third-party DOM scripts only after React has hydrated */}
      <Script
        src="https://example.com/legacy-widget.js"
        strategy="afterInteractive"
      />
    </>
  )
}
```

For Google Translate specifically, the only reliable fix is to **disable the browser's built-in Translate prompt** using a meta tag — Google Translate rewrites text nodes in a way that is fundamentally incompatible with React's hydration:

```html
<!-- In your <head> — disables browser translate prompt -->
<meta name="google" content="notranslate" />
```

## Villain #5: Suspense Boundaries and React 18 Streaming SSR

React 18 introduced streaming server-side rendering via `Suspense`. While this dramatically improves Time to First Byte, it introduces a new class of hydration errors that are trickier to debug.

When you wrap content in `<Suspense>`, React streams a fallback (like a spinner) to the browser first, then streams the resolved content when it's ready. The hydration mismatch happens when the client tries to reconcile a component that was streamed mid-render with a different local state.

```tsx
// ❌ This can cause subtle hydration mismatches with streaming SSR
export default function Page() {
  return (
    <Suspense fallback={<Spinner />}>
      <UserDashboard /> {/* Fetches data async */}
    </Suspense>
  );
}

// Inside UserDashboard — DON'T do this
function UserDashboard() {
  const [theme] = useState(localStorage.getItem('theme')); // ❌ localStorage in SSR!
  // ...
}
```

**The safe pattern with Suspense + streaming:**

```tsx
// ✅ Correct: keep client-only state inside useEffect, not initial state
function UserDashboard() {
  const [theme, setTheme] = useState<string | null>(null); // null = server-safe default

  useEffect(() => {
    setTheme(localStorage.getItem('theme') ?? 'light');
  }, []);

  return <div data-theme={theme ?? 'light'}>...</div>;
}
```

<Callout type="info" title="React 18 Streaming Rule">
  Any component inside a `Suspense` boundary that reads browser APIs must use the `useEffect` + mounted state pattern. The fallback render runs on the server, and the resolved render must match the initial client render exactly before `useEffect` fires.
</Callout>

## Villain #6: `'use client'` Boundary Gotchas (Next.js App Router)

The App Router's Server Component model introduces a new category of hydration errors that didn't exist in the Pages Router. The core rule:

> **Server Components cannot pass non-serializable props to Client Components.**

If you pass a function, a class instance, a Date object, or undefined through a Server → Client component boundary, Next.js will throw an error at build time or cause a silent hydration mismatch at runtime.

```tsx
// ❌ This silently breaks hydration — Date is not serializable over the wire
// app/page.tsx (Server Component)
import ClientWidget from './ClientWidget'; // has 'use client'

export default function Page() {
  const timestamp = new Date(); // Date object — NOT serializable!
  return <ClientWidget createdAt={timestamp} />;
}
```

```tsx
// ✅ Serialize to ISO string first — strings are always safe to pass
export default function Page() {
  const timestamp = new Date().toISOString(); // plain string ✅
  return <ClientWidget createdAt={timestamp} />;
}

// In ClientWidget — reconstruct on the client
'use client'
export function ClientWidget({ createdAt }: { createdAt: string }) {
  const date = new Date(createdAt); // safe to construct on client
  return <div>{date.toLocaleDateString()}</div>;
}
```

**Common non-serializable types that break the boundary:**

| Type | Error | Fix |
| :--- | :--- | :--- |
| `Date` | Silent hydration mismatch | Pass `.toISOString()` string |
| Function | Build error | Move function to Client Component |
| `undefined` | Prop becomes `null` | Use explicit `null` default |
| Class instance | Silent mismatch | Pass plain object `{}` instead |
| `BigInt` | Serialization error | Convert to `String(bigint)` |

For a deep dive into separating Server and Client boundaries in large Next.js apps, see the [Next.js App Router folder structure guide](/en/blog/nextjs-app-router-folder-structure) and the [Next.js App Router caching strategies](/en/blog/nextjs-14-app-router-caching-strategies) guide.

## How to Test for Hydration Errors Before They Hit Production

The best hydration error is one you catch locally, not in a 3am Sentry alert. Here's a testing strategy that catches all four villain patterns before deploy.

### 1. Enable React Strict Mode (it's already on in Next.js)

Next.js enables `<React.StrictMode>` by default. In development, this intentionally renders components twice to surface side effects and hydration issues. If you see a component flash or double-render in dev — that's Strict Mode working. Don't disable it.

### 2. Write a Mounted Guard Unit Test

Use [React Testing Library with user-event v14](/en/blog/react-testing-library-user-event-best-practices) to assert that components render the server-safe default before hydration:

```tsx
import { render, screen } from '@testing-library/react'
import CurrentTime from './CurrentTime'

test('renders server-safe placeholder before mount', () => {
  render(<CurrentTime />)
  // On first render (simulating SSR), should show placeholder
  expect(screen.getByText('Loading time...')).toBeInTheDocument()
})
```

### 3. Check for `suppressHydrationWarning` Overuse

Run this grep before every PR to find suppressed warnings you may have forgotten:

```bash
grep -r "suppressHydrationWarning" src/ --include="*.tsx"
```

Each hit should have a comment explaining why. If there's no comment, it's a hidden bug.

### 4. Use Next.js `--turbopack` dev mode

Turbopack (Next.js 14+) gives more precise hydration error messages than Webpack, including the exact diff between server and client HTML. Enable it:

```bash
next dev --turbopack
```

## Frequently Asked Questions

<Question>
What is a Next.js hydration error?
</Question>
<Answer>
A Next.js hydration error occurs when the HTML rendered on the server does not match what React renders on the client. React compares the server-rendered DOM with its virtual DOM: any mismatch throws Error #418 and forces a full client-side re-render, causing a visible flash of unstyled content.
</Answer>

<Question>
What does "Text content does not match server-rendered HTML" mean?
</Question>
<Answer>
This error means a component outputs different text on the server versus the client. Common causes: rendering `new Date()` or `Math.random()` directly in JSX, using `window`, `localStorage`, or `navigator` without a `typeof window !== 'undefined'` guard, or browser extensions injecting extra DOM nodes that React doesn't expect.
</Answer>

<Question>
How do I fix Error #418 in Next.js?
</Question>
<Answer>
Fix it with one of four approaches: (1) Wrap dynamic client-only content in `useEffect` with a `mounted` state guard so it only renders after hydration. (2) Use the `suppressHydrationWarning` prop on elements with intentional server/client differences like timestamps. (3) Move browser-only code into a `'use client'` component. (4) Use `dynamic(() => import('./Component'), { ssr: false })` for third-party libraries that access `window`.
</Answer>

<Question>
Why does next-themes cause a hydration error?
</Question>
<Answer>
`next-themes` reads the user's color scheme from `localStorage` on the client, but the server renders with the default theme since it has no `localStorage` access. The mismatch causes a flash and hydration warning. The fix is to add `suppressHydrationWarning` to the `<html>` element and use `ThemeProvider` with `attribute="class"`: theme class changes are intentional and can be safely suppressed.
</Answer>

<Question>
How do I safely use localStorage in Next.js without hydration errors?
</Question>
<Answer>
Never read `localStorage` during the initial render. Use a mounted state pattern: initialize state with a server-safe default, then update it inside `useEffect` (which only runs on the client). For example: `const [value, setValue] = useState(null); useEffect(() => { setValue(localStorage.getItem('key')); }, []);`. This guarantees the server and initial client renders are identical before React hydrates.
</Answer>
