Cloud native security has undergone a fundamental architectural shift in 2026. The perimeter is gone. Workloads are ephemeral, clusters span multiple clouds, and the blast radius of a compromised container can be catastrophic without defense-in-depth. Traditional security paradigms—static firewall rules, VPN tunnels, perimeter inspection—cannot model dynamic microservice topologies.

This post covers the four architectural pillars that define cloud native security today: workload identity, supply chain integrity, runtime behavioral defense, and policy-as-code enforcement. Each section includes production-grade configurations with specific tooling.

## Pillar 1: Workload Identity with SPIFFE and SPIRE

The most fundamental shift is replacing network-location-based trust (IP address, VLAN segment) with **cryptographic workload identity**. Every service must prove who it is, not where it is.

**SPIFFE** (Secure Production Identity Framework for Everyone) provides the standard. Every workload gets a SPIFFE ID, expressed as a URI: `spiffe://trust-domain/namespace/workload-name`. The identity is delivered as a short-lived X.509 certificate called a SPIFFE Verifiable Identity Document (SVID), rotated automatically by **SPIRE** (the SPIFFE Runtime Environment).

```yaml
# SPIRE agent ClusterSpiffeID registration via the SPIRE Kubernetes Workload Registrar
apiVersion: spire.spiffe.io/v1alpha1
kind: ClusterSpiffeID
metadata:
  name: payment-service
spec:
  spiffeIDTemplate: "spiffe://prod.example.org/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodMeta.ServiceAccountName }}"
  podSelector:
    matchLabels:
      app: payment-service
  dnsNameTemplates:
    - "payment-service.{{ .PodMeta.Namespace }}.svc.cluster.local"
```

Once SPIRE issues SVIDs, Envoy sidecar proxies use them to establish mutual TLS (mTLS) between every service pair. Istio and Linkerd both integrate with SPIRE via the SPIFFE Workload API.

The critical advantage: even if an attacker compromises a Kubernetes node and accesses the pod network, they cannot forge the SVID of `payment-service` to exfiltrate payment data from `order-service`. The X.509 certificate is cryptographically bound to the workload's identity.

**SVID rotation** is automatic and configurable. For high-security workloads, set a short TTL:

```yaml
# SPIRE Server configuration
server:
  default_svid_ttl: "1h"
  ca_ttl: "24h"
  ca_key_type: "ec-p384"
```

Short TTLs limit the exposure window if a certificate is somehow exfiltrated.

## Pillar 2: Software Supply Chain Integrity

The SolarWinds and XZ Utils attacks demonstrated that the build pipeline itself is an attack surface. In 2026, supply chain security is mandatory for regulated industries and increasingly expected everywhere.

### SLSA (Supply-chain Levels for Software Artifacts)

SLSA Level 3 requires:
1. **Scripted builds** — no manual build steps
2. **Source version controlled** — signed commits
3. **Build service** — hermetic, isolated build environment (GitHub Actions, Google Cloud Build)
4. **Provenance** — signed attestation of what was built and how

Generate SLSA provenance automatically in GitHub Actions:

```yaml
# .github/workflows/build.yml
jobs:
  build:
    permissions:
      id-token: write
      contents: read
      attestations: write
    steps:
      - uses: actions/checkout@v4
      - name: Build container image
        run: |
          docker build -t myapp:${{ github.sha }} .
          docker push registry.example.com/myapp:${{ github.sha }}
      
      - name: Attest build provenance
        uses: actions/attest-build-provenance@v1
        with:
          subject-name: registry.example.com/myapp
          subject-digest: sha256:${{ steps.build.outputs.digest }}
          push-to-registry: true
```

### SBOM Generation and Continuous Evaluation

Every container image should have a signed SBOM in SPDX or CycloneDX format. Syft generates them; Grype evaluates them against the NVD in real time:

```bash
# Generate SBOM attached to the image
syft registry.example.com/myapp:latest \
  -o spdx-json \
  --file myapp-sbom.spdx.json

# Evaluate against CVE databases
grype sbom:myapp-sbom.spdx.json \
  --fail-on critical \
  --only-fixed
```

Integrate this into CI as a required gate. If a zero-day is disclosed after deployment, your SBOM inventory immediately tells you which running workloads are affected — enabling targeted remediation instead of panic-patching everything.

### in-toto Supply Chain Attestation

For the highest assurance, in-toto records cryptographic evidence of every step in the supply chain — from developer commit to container image push:

```python
# in-toto link metadata for the "build" step
import in_toto.runlib

link = in_toto.runlib.in_toto_run(
    name="build",
    link_signing_key=signing_key,
    material_paths=["src/", "requirements.txt"],
    product_paths=["dist/app.tar.gz"],
    run_command=["python", "setup.py", "build"]
)
link.dump("build.link")
```

The chain of `.link` files provides a court-admissible evidence trail from source to artifact — something a compromised CI system cannot fake without the developer's signing key.

## Pillar 3: Runtime Defense with eBPF

Preventative measures are necessary but insufficient. A zero-day vulnerability or a misconfigured container can still result in a compromised process. Runtime security provides the behavioral enforcement layer.

**eBPF** (extended Berkeley Packet Filter) runs sandboxed programs inside the Linux kernel, providing zero-overhead visibility into system calls, file access, and network connections without modifying application code or loading kernel modules.

**Tetragon** (from Cilium) translates eBPF kernel events into enforcement policies:

```yaml
# Tetragon TracingPolicy: block shell execution from web service pods
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: prevent-shell-from-web
spec:
  kprobes:
  - call: "sys_execve"
    syscall: true
    selectors:
    - matchNamespaces:
      - namespace: production
        values: [web-service]
      matchArgs:
      - index: 0
        operator: "Equal"
        values:
        - "/bin/sh"
        - "/bin/bash"
        - "/usr/bin/python3"
        - "/usr/bin/curl"
      matchActions:
      - action: Sigkill
        argName: comm
```

This policy kills any process that attempts to `execve` a shell within the `web-service` production pods — instantly containing RCE attempts even if the underlying CVE was previously unknown.

**Cilium Network Policy** enforces Layer 7 (HTTP/gRPC) access control at the kernel level:

```yaml
apiVersion: cilium.io/v1
kind: CiliumNetworkPolicy
metadata:
  name: payment-service-policy
spec:
  endpointSelector:
    matchLabels:
      app: payment-service
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: order-service
    toPorts:
    - ports:
      - port: "8080"
        protocol: TCP
      rules:
        http:
        - method: "POST"
          path: "/v1/charge"
```

Only `order-service` can call `POST /v1/charge` on `payment-service`. Any other traffic — including internal lateral movement from a compromised pod — is dropped at the kernel level before it reaches the application.

## Pillar 4: Policy as Code with OPA Gatekeeper

Kubernetes admission control enforces cluster-wide security policies at deployment time. OPA Gatekeeper evaluates every API server request against Rego policies:

```rego
# Deny containers running as root
package kubernetes.admission

deny[msg] {
  input.request.kind.kind == "Pod"
  container := input.request.object.spec.containers[_]
  not container.securityContext.runAsNonRoot == true
  msg := sprintf("Container '%v' must not run as root. Set securityContext.runAsNonRoot: true", [container.name])
}

# Require read-only root filesystem
deny[msg] {
  input.request.kind.kind == "Pod"
  container := input.request.object.spec.containers[_]
  not container.securityContext.readOnlyRootFilesystem == true
  msg := sprintf("Container '%v' must have a read-only root filesystem", [container.name])
}
```

These policies block insecure pod deployments before they reach the scheduler. Combined with GitOps (Flux v2, ArgoCD), your cluster state is entirely policy-gated — no manual `kubectl apply` can bypass admission control.

## Defense in Depth Architecture

The four pillars stack into a coherent defense-in-depth model:

| Layer | Tool | What It Blocks |
|---|---|---|
| Identity | SPIFFE/SPIRE + mTLS | Network spoofing, lateral movement |
| Supply chain | SLSA + SBOM + in-toto | Compromised builds, malicious dependencies |
| Runtime | Tetragon eBPF | RCE, shell spawning, data exfiltration |
| Policy | OPA Gatekeeper | Misconfigured workloads, privilege escalation |

No single layer is sufficient. An attacker who bypasses identity (stolen SVID) still hits runtime behavioral detection. A compromised build that passes SBOM checks still faces OPA policy enforcement at admission.
